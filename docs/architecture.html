1 What this app is

The problem. A student uploads their notes or a scanned question paper and needs real study material fast — not just a summary that sounds convincing. Most "summarize my notes" tools mix what's actually in your notes with things the AI already knows about the topic, blended together so smoothly you can't tell which is which. For someone studying for an exam, that's a real risk — you might study something your professor never taught, or trust something the AI just made up.

What "verified" means here. Two separate things:

  1. Honest about where it came from — every explanation is split into two clearly labeled parts: "from your notes" (only what your notes actually say) and "explained further" (anything extra, clearly marked as added). This isn't a check done afterward — it's built into how the AI is asked to write in the first place.
  2. Double-checked by a second AI — once flashcards and quiz questions are written, a different AI (Groq, not the one that wrote them) checks whether each one is actually true and actually about the right topic, before the student ever sees it.

Why not just one big "summarize this" request. The obvious simple approach is one prompt: "here's my notes, give me a summary, flashcards, and a quiz." We didn't do that. Asking one AI request to do four different jobs at once (summarize, make flashcards, make a quiz, and stay honest about sourcing) tends to produce a mediocre version of all four, because the AI's effort gets split across competing goals in a single answer. Instead, this app breaks the work into steps — first figure out the topics, then generate each type of content per topic, one focused request at a time. More total requests, more code to manage, but each individual piece comes out better.

Alternative not picked: one big request

Pros: far fewer AI calls (cheaper, faster, less code).

Cons: no natural way to double-check individual claims (you'd be checking one giant answer, not small provable pieces), no way to make "how simple" and "how deep" genuinely change the structure of each topic individually, and no easy way to later fix just one weak topic without redoing everything.

What would actually change in the code: there'd be no separate "figure out the topics" step and no per-topic loop — pipeline.py would shrink to one function making one big request, and the double-checking step would either disappear or become much cruder (checking "does this whole answer look okay?" instead of "is this exact flashcard true?").

Why two separate settings (Style and Depth) instead of one. Many similar tools use a single slider like "Beginner / Advanced." That mixes up two different things: how something is said (simple words vs. technical language) and how much exists (a quick overview vs. full detail). Someone might want plain, simple language but still want the complete, deep explanation — those aren't the same request, and a single slider can't tell them apart.

Alternative not picked: one combined setting

Pros: simpler to build, simpler for the user to understand at a glance.

Cons: forces the assumption that "simple" always means "shallow," which isn't true for everyone.

What would actually change in the code: style_rules.py keeps two separate rule tables today — one for wording, one for structure — that get combined per request. A single-setting version would merge these into one table, and every function that currently takes two separate settings would take just one, less flexible one.

2 Tech stack: what & why

Streamlit (the whole user interface)

What it is. Streamlit is a Python library that turns a plain Python script into a working web app — no separate frontend code (no HTML/CSS/JavaScript you have to write), no separate backend API. You write Python that says "show a button here, a text box there," and Streamlit turns that into a real webpage automatically.

Why we used it. This is a solo project built to actually finish and work, not a production product with thousands of users. Streamlit lets one person build a real, usable app entirely in Python, fast — no need to learn or maintain a separate web framework (like React) plus a separate API layer (like Flask or FastAPI) plus glue code between them. Every UI decision in this app — buttons, tabs, file uploads, the whole layout — is one Python file, app.py.

How it actually behaves (important, and unusual). Every time you click anything — a button, a tab, a dropdown — Streamlit doesn't just update that one thing. It re-runs your entire Python script from the top, every time. Nothing "stays alive" between clicks except a special dictionary called session_state, which is the only way to remember anything (like "a document is currently selected" or "a button was just clicked") across those re-runs. This sounds wasteful, but for an app this size it's fast enough, and it's why several odd-looking patterns exist in the code (explained properly in Section 11).

Alternative: a real frontend + backend (e.g. React + FastAPI)

Pros: far more control over exactly how things look and animate, true instant interactions with no server round-trip needed for simple UI state changes, easier to eventually support many users at once.

Cons: massively more code to write and maintain — two separate codebases in two different languages, needing an API contract between them, deployment of two separate things instead of one. For one person building a personal study tool, that's a lot of extra weeks of work for benefits (scaling to many users, polished animations) that don't matter here.

What would actually change in the code: app.py wouldn't exist at all. There'd be a frontend/ folder full of React components, and everything currently living in agents/, services/, and export/ would instead sit behind API endpoints (e.g. POST /generate, GET /documents/:id) that the frontend calls over the network. The two-phase busy pattern, the tab-reset issue, the click-blocking overlay — none of those specific problems would exist, because a real frontend can update just one piece of the page without re-running everything else. But a whole new category of problems would show up instead: authentication, API versioning, CORS, deploying two services instead of one.

Gemini / the google-genai SDK (the content-generation model)

What it is. Gemini is Google's family of AI models. google-genai is the official Python library for calling Gemini over the internet. This app specifically uses gemini-3.5-flash-lite — the smallest, fastest, cheapest tier of the Gemini family.

Why we used it. Free tier availability was the deciding factor for a personal project with no budget — Gemini's free tier gives a genuinely usable daily quota (500 requests/day for this specific model) without needing a credit card. flash-lite specifically was chosen for speed and cost over the more capable flash or pro tiers, since this app makes many calls per document (one per concept, times three — summary, flashcards, quiz), so per-call cost and speed matter more here than in an app that makes one call per session.

The tradeoff we actually hit. A smaller/faster model like flash-lite is noticeably worse at reliably following complicated instructions — this showed up directly and repeatedly this session, most clearly in the PYQ answer-length saga (Section 7), where the same instruction sometimes worked and sometimes didn't, purely due to model unreliability, not our wording.

Alternative: a bigger Gemini tier, or a different provider (OpenAI GPT, Anthropic Claude)

Pros: more reliable instruction-following, likely better quality answers with less prompt engineering needed to compensate.

Cons: real dollar cost per request instead of free, and/or a much smaller free daily quota — a serious problem for a project that got tested this heavily in one session (we hit Gemini's daily free quota more than once just from testing).

What would actually change in the code: almost nothing structurally — gemini_client.py's generate_json() function is the only place that actually calls the Gemini API; every agent goes through it. Switching providers would mean rewriting that one file to call a different SDK, and possibly loosening some of the very specific prompt-engineering workarounds we had to build because flash-lite is unreliable (the content-forcing PYQ length spec, the thinking-budget trick) — a more capable model might not need them at all.

Groq (the independent verification model)

What it is. Groq is a different company from Google, running its own AI models on their own specialized hardware built for very fast inference. This app uses Groq to run openai/gpt-oss-120b (an open-weight model, not one of Groq's own) specifically for the verification step — checking whether generated flashcards/quiz questions are actually true and on-topic.

Why a second, different provider, not just a second Gemini call. If the same model checks its own work, it's likely to make the same kind of mistake twice — a blind spot in Gemini's reasoning is likely to also be a blind spot when Gemini is asked "did you get that right?" A genuinely different model, from a different company, trained differently, is much less likely to share the exact same blind spots. This is the entire reason verification runs on Groq and not Gemini.

Alternative: verify with Gemini too (a second Gemini call with a "check this" prompt)

Pros: one less API integration to maintain, one less thing that can independently break.

Cons: weaker independence guarantee — exactly the blind-spot risk above.

What would actually change in the code: agents/verifier.py would call gemini_client.generate_json instead of groq_client.generate_json, and services/groq_client.py wouldn't need to exist as a separate file. Functionally the verify step would look almost identical in code — really a one-line swap — but the guarantee it provides would be meaningfully weaker.

SQLite (the database)

What it is. SQLite is a database that lives entirely as a single file on disk (data/studymate.db) — no separate database server process to install, start, or manage. Python has built-in support for it (the sqlite3 module), so no extra installation was even needed.

Why we used it. This app runs on one person's machine, used by one person, at a time. A "real" database server (like PostgreSQL or MySQL) is built for many simultaneous users and processes talking to it over a network — none of which applies here. SQLite gives exactly what's needed (structured storage, relationships between tables, the ability to query) with zero setup overhead.

Alternative: PostgreSQL

Pros: handles many simultaneous users properly, more advanced features (better concurrent-write handling, more powerful querying).

Cons: requires installing and running a separate database server process, plus connection configuration — real setup overhead for a single-user local app that gets zero benefit from those features.

What would actually change in the code: services/db.py would look almost the same at the function level (create_document, list_concepts, etc. would still exist and do the same jobs) but every raw SQL query would need to go through a proper connection pool instead of opening/closing a fresh file connection per call, and the whole app would need a running Postgres server as a dependency before it could even start — a real deployment step that doesn't exist today.

Jinja2 (the export template engine)

What it is. Jinja2 is a Python templating library — you write an HTML file with placeholders (like {{ title }} or {% for concept in concepts %}) and Jinja2 fills them in with real data to produce a final HTML file.

Why we used it. The downloadable study-pack HTML file needs real content — every concept, every flashcard, every quiz question — inserted into a fixed page layout. Jinja2 is the standard, well-tested way to do exactly that in Python, and it was effectively required the moment we decided the export should be templated HTML rather than built up manually with string concatenation.

Alternative: build the HTML by hand with Python string joining

Pros: no extra library dependency.

Cons: quickly becomes unreadable and bug-prone once you need loops (one block per concept) and conditionals (only show a section if it has content) mixed into HTML — which is exactly what the export template needs throughout.

What would actually change in the code: export_builder.py's build_html() would replace template.render(...) with a much longer function manually gluing strings together, and html_template.html would stop being a clean, readable template file and would instead be scattered across Python string literals.

xhtml2pdf (the PDF export)

What it is. A pure-Python library that converts HTML+CSS into a PDF file.

Why we used it. The PDF export needed to happen without asking the user to install anything extra on their machine (some popular alternatives require separate non-Python system software). xhtml2pdf installs with a normal pip install and nothing else, which mattered a lot for a personal Windows setup with no appetite for wrestling with system-level dependencies.

Alternative: WeasyPrint (a more powerful, more accurate HTML-to-PDF renderer)

Pros: much better CSS support (handles modern layout like flexbox and CSS variables, which xhtml2pdf can't), generally nicer-looking output.

Cons: requires installing separate system libraries (Pango, Cairo — graphics libraries, not Python packages) outside of pip, a well-known source of installation pain specifically on Windows.

What would actually change in the code: if WeasyPrint had been used, the PDF export could likely have reused the same interactive HTML template instead of needing a second, simplified pdf_template.html built with plain CSS. The separate, simpler PDF template exists specifically because xhtml2pdf can't handle that CSS.

pypdf, python-docx, python-pptx (reading uploaded files)

What they are. Three separate Python libraries, one per file type, each knowing how to open that specific file format and pull the text out of it: pypdf for PDFs, python-docx for Word documents, python-pptx for PowerPoint slides.

Why we used them. There's no single library that reads all three formats — each file format has its own internal structure, so a dedicated library per format is the normal approach. All three are the standard, most widely-used Python libraries for their respective formats.

Alternative: a general-purpose "extract text from any document" service (e.g. cloud OCR, Apache Tika)

Pros: one integration instead of three, possibly better extraction quality for tricky layouts.

Cons: either costs money per use, or requires running a separate service (Tika needs a running Java process) — real overhead compared to three lightweight, free, pure-Python libraries that just work locally.

What would actually change in the code: note_parser.py's three separate parse_pdf/parse_docx/parse_pptx functions would collapse into one function calling out to whatever the general service's API looks like — simpler code, but a new external dependency where there currently is none.

3 Style & Depth, the two axes

What each one actually controls.

Style (Simple / Standard / Technical) changes how things are said — vocabulary, sentence length, and how much jargon gets explained versus assumed. At Simple, sentences stay short (around 15 words), and every technical term gets explained the moment it's used, even ones that might seem basic. At Technical, the app assumes real background knowledge and writes the way a textbook in that field would.

Depth (Overview / Standard / Deep dive) changes how much exists — not just longer writing, but genuinely different amounts of content and structure: how many topics the notes get split into, how many fields each topic's explanation has, how many flashcards and quiz questions get made, and how long/structured an exam-answer example is.

Why these had to be genuinely structural, not just "write more words." Early on, it would have been easy to fake Depth by just telling the AI "write a longer answer" at Deep dive. That's not what happens here — different depths ask for different fields to exist at all, different numbers of topics, different counts of everything downstream. The reason: a real difference a student can see and rely on (this Depth gives me way more flashcards and a comparisons section; this one doesn't) is much more trustworthy than a subtle "well, the paragraphs are a bit longer I guess."

Alternative not picked: control length with a single "write N words" instruction

Pros: much simpler to write and reason about — one instruction, one number.

Cons: this was tried, repeatedly, in a related but separate part of the app (the exam-answer feature for question papers) — and small/fast AI models turned out to be bad at reliably hitting a target word count. They'd satisfy the letter of "write more" with padding or repetition rather than genuinely writing more content.

What would actually change in the code: if length instructions had been used instead, style_rules.py's DEPTH_PARAMS table (concept counts, flashcard counts, quiz counts, which explanation fields exist) wouldn't need to exist at all — depth would just be one line in a prompt, and the app would have no way to guarantee a real structural difference, only hope the AI actually delivered one.

Exactly what gets added at each depth

The explanation itself grows by adding internal building blocks, not by "writing more." Every concept's main explanation is actually assembled from up to three separate pieces, and how many of those pieces exist is exactly what Depth controls:

DepthPieces used to build the explanation
Overviewexplanation_core only — what the concept is and how it works, nothing else
Standardexplanation_core + explanation_detail — adds a specific mechanism or nuance that genuinely isn't already covered in the core piece
Deep diveexplanation_core + explanation_detail + explanation_example — adds a concrete real-world scenario showing the concept in action

These three pieces get joined together (with a blank line between them) into what the student sees as one continuous "explained further" section — so a Deep dive concept isn't "the same paragraph but longer," it's genuinely three distinct, separately-generated pieces of content stitched together, each doing a different job.

4 The full user journey

This section walks through what actually happens on screen, step by step, from opening the app to holding a finished study pack — and at each fork in that path, why it was built that way instead of some other reasonable way.

Two entry points, one pipeline

A student can start from either the sidebar's "Upload new notes" section or its "...or solve a question paper (PYQ)" section — upload their own notes, or upload a previous-year question paper instead (or a photo of one). These feel like two different features, but underneath they run through the same generation pipeline. For a PYQ upload, the questions themselves get read out first and are then treated exactly like "notes" for everything downstream — the same concept-extraction step, the same per-concept summary/flashcard/quiz generation. The only genuinely separate thing that happens afterward is writing model answers to the actual questions.

Alternative not picked: two separate, independent features

Pros: each path could be tuned and reasoned about in complete isolation, with no risk of a change to one accidentally affecting the other.

Cons: a PYQ upload still needs a concept summary, flashcards, and a quiz — a student solving past papers still needs to actually learn the material, not just see model answers. Building that a second time, separately, would mean writing (and later fixing bugs in) the same concept-extraction and content-generation logic twice.

What would actually change in the code: pipeline.py's generate_from_pyq function wouldn't exist as a thin wrapper around generate_study_material — it would be its own, separately maintained copy of the whole per-concept generation loop, with its own copies of the same bugs to find and fix independently.

Who actually receives the call, and who it passes through — agent by agent

Two different kinds of things exist in this codebase, and it matters which one you're talking about:

  • The 8 agents — each one does exactly one AI-generation job and nothing else. None of them know about each other. None of them call each other.
  • The Pipeline — not an agent itself, and not the same thing as the Orchestrator agent (easy to mix up because the names sound similar). The Pipeline is the coordinator that sits above all 8 agents, calls them one at a time in a fixed order, and passes the result of one into the next. Every agent hands its result back to the Pipeline, not directly to the next agent.

So when "Generate study material" is clicked, the click goes to the Pipeline first — never straight to an agent. From there, here is exactly which agent gets called, in what order:

  1. Orchestrator is the first agent called, and only once per document. Its only job: read the whole notes and return the list of topics (concepts). Nothing else has happened yet — no explanations, no flashcards, nothing — just the table of contents for the document.
  2. Then, for each topic in that list, one at a time, in this fixed order:
    1. Summarizer — writes that one topic's explanation.
    2. Flashcard Maker — writes flashcards for that same topic.
    3. Verifier — checks those flashcards (this is a completely different agent from the one that wrote them, deliberately, see Section 6).
    4. Quiz Maker — writes quiz questions for that same topic.
    5. Verifier — checks those quiz questions too (the same Verifier agent, called a second time for this topic).
    Only once all five of those steps are done for one topic does the Pipeline move on to the next topic and start that same five-step sequence again from Summarizer.

Is this sequential or parallel? Strictly sequential — nothing here runs at the same time as anything else. Topic 2 does not start until every one of the five steps for Topic 1 has completely finished. Within one topic, the five steps also happen strictly in that order — Quiz Maker never starts before Flashcard Maker's result has already come back and been checked by the Verifier. There is no point anywhere in this whole process where two agents are doing work at the same moment.

Why sequential, when several of these steps don't actually depend on each other. Flashcard Maker and Quiz Maker for the same topic genuinely don't need each other's output — they could, in principle, run at the same time. Two different topics also don't depend on each other at all — Topic 5's flashcards have nothing to do with Topic 2's summary. Running things in parallel would very likely make the whole process noticeably faster. It isn't done here because of how Streamlit itself works (Section 2 and Section 11): the entire app is one single script running top to bottom, with no separate background workers set up to run things at the same time. Adding real parallelism would mean introducing a genuinely different piece of machinery (background threads or async tasks) purely to manage that — a bigger architectural change than this project's scale called for, so simple, predictable, one-thing-at-a-time execution was accepted instead.

Two agents sit slightly outside this main sequence:

  • Vision Reader is called before the Pipeline even starts, only if the student uploaded photos of notes instead of a text-based file — it turns the photos into plain text first, and that text is what the Pipeline receives as "notes." Vision Reader never talks to Orchestrator or any other agent directly.
  • PYQ Solver only gets involved for a question-paper upload, and it's called at two completely different points, not as part of the topic-by-topic loop at all: once before the Pipeline starts (to read the questions off the paper and turn them into text, the same role Vision Reader plays for photographed notes), and once after the entire Orchestrator → Summarizer → Flashcard Maker → Verifier → Quiz Maker → Verifier sequence has completely finished for every topic (to actually write the model answers, now that topics exist to match answers against). So a question-paper upload runs everything a plain-notes upload runs, plus PYQ Solver bookending it on both sides.

Style Rules — the one thing every agent actually shares

One more piece is worth naming here even though it never gets "called" the way the others do: Style Rules isn't an agent (it never talks to an AI model), but every single agent above reads from it before it writes its own request — it's where the current Style and Depth settings actually live as concrete rules and numbers (the tables in Section 3 come from here). So really, every arrow in the sequence above is also quietly touching Style Rules first, even though it's not part of the main call chain.

Why a plain coordinator (the Pipeline) instead of an orchestrator agent

A reasonable alternative design: instead of a fixed, hardcoded order, have one AI agent whose actual job is deciding, in the moment, "call Summarizer next," "now call Flashcard Maker," and so on — using its own reasoning rather than a sequence a programmer wrote down in advance. That's a real, named pattern in agentic AI design (often called an orchestrator-agent or supervisor-agent pattern). We didn't build it that way, for one specific reason: the sequence of who gets called never actually varies. Every time, for every document, the order is identical. There is no situation here where the right next step depends on judgment — it's a fixed recipe, not a decision.

Alternative not picked: an LLM-based orchestrator agent that decides the call sequence itself

Where this would genuinely earn its keep: a task where the right next step really does depend on judgment — e.g. "the Verifier keeps rejecting this topic's flashcards, should I regenerate them, skip flashcards for this topic, or ask the Summarizer to expand the explanation first?" That's a real decision an intelligent orchestrator could improve on. Our current pipeline doesn't do that kind of adaptive branching anywhere — it just fails a check and moves on (Section 6's "fails open" behavior).

Cons of building it anyway: an extra AI call, every single step, just to decide something that never actually needs deciding (real added cost and time for zero gained flexibility); new unpredictability on purpose, for a task that doesn't want any (an LLM-decided flow could skip a step or reorder things differently on a technically identical rerun); and much harder to debug — a fixed pipeline fails at a known line, every time, while an LLM-decided flow can take a different path on two runs of the same input.

What would actually change in the code: pipeline.py's plain function calls and for-loop would be replaced by a new agent whose entire job is routing — reading the current state and deciding which of the other 8 agents to call next, in a loop, until it decides the document is done. That agent would need its own careful prompt design (what does "done" mean, how does it avoid infinite loops, how does it recover from a bad decision) — real added complexity, for a task where the current fixed order has never actually needed to change.

Single-agent or multi-agent system?

Multi-agent. There are 8 distinct agents, each specialized in one job, each independently calling an LLM to do that job — that's the basic definition of multi-agent. But multi-agent systems aren't all the same shape, and it's worth being precise about which shape this one is:

  • Peer-to-peer / conversational — agents talk directly to each other, negotiate, or critique each other's work. Not this app. No agent here has ever seen another agent's raw output as a conversation partner — Verifier doesn't talk to Flashcard Maker, it just receives what Flashcard Maker produced, handed to it by the Pipeline.
  • Orchestrator-agent / supervisor pattern — a central agent (itself LLM-driven) decides who to call and when, adaptively. Not this app either — the coordinator (the Pipeline) is plain deterministic code, not an agent, and the sequence is fixed in advance by the programmer, not decided at runtime.
  • Sequential / pipeline pattern — a fixed, predetermined sequence of specialized agents, coordinated by a non-agent controller. This is exactly what StudyMate AI is.

The precise, defensible answer: it's a multi-agent system using a sequential pipeline architecture, with centralized coordination handled by deterministic code rather than by an LLM-based orchestrator or by agent-to-agent communication — 8 separate agents, acting one after another, coordinated by a plain code layer, never talking to each other directly.

Style and Depth are chosen once, up front

Both settings are picked at upload time, before generation starts — not something you can change per-section afterward, and not something re-asked later (e.g. when taking the quiz, or when a weak topic gets remediated; remediation reuses the document's original Style/Depth automatically, see Section 8).

Alternative not picked: adjustable per-section, after generation

Pros: more flexible — a student could read Overview first for a quick pass, then re-read the same topic at Deep dive without generating a whole new document.

Cons: Depth doesn't just change wording, it changes how many concepts exist in the first place (Section 3) — Overview might merge two ideas into one concept that Deep dive would split apart. Changing Depth after the fact isn't "show more text," it's "regenerate the whole concept structure," which is really a new document, not a setting toggle on an existing one.

What would actually change in the code: concepts, flashcards, and quiz questions would need to store which Style/Depth they were generated at, and the UI would need a way to regenerate just one concept at a new Depth without touching the others — a real feature that doesn't exist today; right now Style/Depth belong to the document (documents.explanation_style, documents.depth_level in the database), not to each individual piece of content.

Generation is one long blocking step, not a progressive reveal

Clicking "Generate study material" shows a growing checklist (topic names turning green as each one finishes) but doesn't let you look at the first finished topic while the rest are still generating — the whole document becomes available all at once, at the end. While it's running, the entire rest of the app is deliberately disabled (a full-page overlay, explained in Section 11), not just the button you clicked.

Alternative not picked: reveal each concept as soon as it's ready, let the student start reading immediately

Pros: feels faster — you'd start reading the first topic while later ones are still being generated in the background, instead of watching a checklist and waiting.

Cons: Streamlit's execution model (Section 2/11) makes true background work while the UI stays interactive a real engineering project of its own — by default, the script that's generating content is the same script rendering the page, so "let the student browse while generation continues" would need a fundamentally different architecture (a background worker process, a job queue, polling for progress) rather than the one-process, one-script design this app uses everywhere else.

What would actually change in the code: pipeline.generate_study_material's per-concept loop would need to run somewhere other than directly inside the Streamlit script — a background thread or separate process — with app.py polling it for progress instead of calling it directly and waiting. That's a substantially different app, not a small change to this one.

The five-tab result view

Once generated, a document opens into five tabs: Summary (every concept's explanation), Flashcards, Quiz, Progress dashboard (per-concept status: cleared, still learning, flagged), and — only if the document came from a question paper — PYQ Solutions. The quiz grades itself instantly inside the app (no AI call involved in grading — it's just comparing your selected answer to the stored correct index), and answering enough questions wrong on a topic marks it weak, surfaced on the Progress dashboard with a "Fix weak topics now" button.

Why remediation is a button the student clicks, not something that happens automatically the moment a topic is detected as weak. Automatically regenerating content the instant a threshold is crossed would mean firing off real AI calls (cost, time, and — see Section 11 — a full-page block on the rest of the app) as a side effect of just answering quiz questions, with no chance for the student to finish the quiz first or decide they'd rather come back to it later.

Alternative not picked: automatic remediation the moment a topic crosses the weak threshold

Pros: one less click, feels more "adaptive" in the moment.

Cons: triggers expensive AI work as a side effect of answering a single question, potentially mid-quiz, and takes away the student's ability to just finish the quiz first and decide afterward whether they want to fix anything right now.

What would actually change in the code: the weak-topic check (adaptive_loop.is_weak) currently only decides whether to show the "Fix weak topics now" button — it doesn't call run_remediation itself. An automatic version would call it immediately after grading, inside the same code path that records a quiz answer, turning a simple, fast, local grading action into one that might unpredictably take many seconds and consume API quota.

Export, at the very end

Once satisfied, the student can download the whole document as a self-contained HTML file (interactive — flippable flashcards, a working in-browser quiz, adjustable reading theme) or as a PDF (static, print-friendly, everything pre-revealed since paper can't be clicked). Both are offered as separate, independent downloads, not a single combined format.

Alternative not picked: one export format that covers both use cases

Pros: one button instead of two, one template to maintain instead of two.

Cons: an interactive, click-to-flip flashcard or a JavaScript-graded quiz simply doesn't exist on paper — a PDF has no JavaScript at all. The two formats have genuinely incompatible requirements (interactive-and-hidden vs. static-and-revealed), not just a styling difference.

What would actually change in the code: this was tried, in effect, at the code level — the PDF export deliberately does not reuse html_template.html (Section 10 covers why in full); it has its own separate, simpler template. A single-format approach would mean picking one of those two designs and losing the other's benefit entirely (either a PDF with dead click-to-flip cards that don't work on paper, or an HTML export with everything pre-revealed and no interactivity even though a browser could support it).

5 The generation pipeline

Section 4 traced which agent gets called, in what order. This section goes one level deeper — the design decisions living inside the Pipeline itself, around and between those agent calls, that make the whole thing reliable rather than just functional.

The grounding-text pattern

Flashcards and quiz questions for a concept aren't generated against the raw notes alone — they're generated (and later verified) against the notes plus that concept's own explanation, which was just written by the Summarizer a moment earlier. That combined text is what gets called "grounding text" throughout the codebase.

Why this matters, concretely. A concept the student typed in manually (the "extra concepts" field) might not be mentioned in the uploaded notes at all — that's the whole point of letting someone add a concept themselves. If flashcards for that concept were generated and checked against the notes alone, there'd be nothing in the notes to ground them in: the Verifier would correctly reject everything as unsupported, and that concept would end up with zero flashcards and zero quiz questions, silently. Grounding against the concept's own explanation too means there's always real, checkable material to work from and verify against, even for a concept the notes never mention.

Alternative not picked: ground flashcards/quiz in the raw notes only

Pros: simpler to reason about — "grounded in the notes" means exactly what it sounds like, no second source involved.

Cons: this was tried, in effect, before the pattern existed, and it produced exactly the failure described above — manually-added concepts systematically ended up empty, because there was nothing in the notes to generate or verify real content against.

What would actually change in the code: the one line in pipeline.py that builds grounding_text by combining notes and the concept's summary would just pass the raw notes straight through instead — a tiny code change with a large, systematic content-quality consequence.

Saving progress as it happens, not all at once at the end

A document row is created in the database the moment generation starts — before a single concept has been written. Each concept's summary is saved the instant it's generated, before its flashcards even begin. Flashcards are saved before the quiz for that concept starts. Nothing is held in memory and written out in one big batch at the very end.

Alternative not picked: build the whole document in memory, write it to the database once at the end

Pros: fewer, larger database writes instead of many small ones; slightly simpler code (no need to think about "what if we stop partway through").

Cons: if anything interrupts generation partway through — a Gemini daily quota running out (a real thing that happened repeatedly during testing), a network failure, the student clicking Stop — an all-at-the-end design loses everything generated so far, even concepts that finished perfectly minutes earlier. Writing incrementally means a run that dies on concept 6 of 9 still leaves a real, usable document with 5 complete concepts in it, not nothing.

What would actually change in the code: pipeline.py's many small db.add_flashcard/db.update_concept_summary/etc. calls scattered through the per-concept loop would collapse into one big write after the entire loop finishes — and every one of those try/except/finally patterns in app.py that exist specifically to handle a run stopping partway through (Section 11) would have nothing left to save when that happens.

Where concepts come from, and how two sources get merged

Every concept has a source: "auto" (found by the Orchestrator) or "manual" (typed in by the student in the "extra concepts" field). The manual ones are added after the Orchestrator's own call returns, checked against what the Orchestrator already found (case-insensitively, so "Price Elasticity" and "price elasticity" count as the same one) and only appended if genuinely new — never folded into the prompt the Orchestrator itself sees.

Alternative not picked: include the student's requested concepts in the Orchestrator's own prompt

Pros: one unified step instead of an extraction call plus a separate merge step.

Cons: an AI call is still just a request, not a guarantee — asking the Orchestrator to "make sure to include X" doesn't actually guarantee X survives in its returned list; it might still merge X into a broader concept, rename it, or drop it if it judges it out of scope. A concept the student explicitly typed in needs to be guaranteed to exist, not just requested.

What would actually change in the code: orchestrator.extract_concepts would fold extra_concepts into its own prompt text and return one combined list, with no separate merge step in pipeline.py afterward — simpler, but with no code-level guarantee a manually-requested concept actually made it into the final list.

Two layers of defense before content is trusted

Immediately after Flashcard Maker or Quiz Maker responds, and before anything reaches the Verifier, pipeline.py runs its own shape-filtering pass — no AI involved, just plain code checking whether what came back is actually usable: is this really a dict with the right keys, are the required fields actually present and non-empty, is correct_index a valid number pointing at a real option, does a field look like it accidentally contains raw JSON instead of a real answer (a known model glitch). Anything that fails this check is thrown away right there — it never gets sent to the Verifier at all.

Only what survives shape-filtering moves on to verification — the real second AI call, to Groq. The surviving items are numbered and sent in one batch, with a prompt asking Groq to judge each one on two separate questions: is it grounded (actually true according to the grounding text) and is it relevant (actually about the concept it's filed under, not some other true-but-different topic). Groq returns a verdict per item; only the ones marked valid are saved to the database. (The full mechanics of how this check itself is designed — why Groq specifically, what happens if the check fails, the history of why both groundedness and relevance get checked — is covered in full in Section 6.)

Alternative not picked: skip shape-filtering, send everything straight to the Verifier

Pros: one less layer of code to maintain.

Cons: shape-filtering is free and instant — no API call, no cost, no wait. Skipping it means spending a real Groq call (and Section 6 explains Groq's per-minute token budget is genuinely tight) verifying content that was already malformed and was always going to be discarded regardless of what the verifier said about it.

What would actually change in the code: the shape-filter list-comprehensions sitting between each agent call and each verifier.verify_* call in pipeline.py would disappear, and verifier.py would need to become defensive enough to handle genuinely malformed input gracefully instead of assuming it always receives well-formed items.

Deduplication across the whole document, not just within one concept

Flashcards are checked for near-duplicates against every flashcard generated so far in the document, not just the ones from the same concept. Two concepts that are closely related can easily produce very similar flashcards (e.g. "innovation" showing up as its own flashcard under two different but related topics) — checking only within one concept wouldn't catch that at all.

The check itself is a similarity comparison (not exact-text matching) with a threshold of 0.75 — normalized text (lowercased, punctuation stripped) that's 75% or more similar to something already kept gets rejected as a duplicate. Notably, this same dedup logic is reused, unchanged, by the remediation loop (Section 8) when it adds drill flashcards later — a new drill card gets checked against everything already in the document, not just against other drill cards, so remediation can't quietly reintroduce a card that's nearly identical to one that already exists.

Alternative not picked: exact-text duplicate checking instead of similarity-based

Pros: simpler, faster, completely unambiguous — either the strings match or they don't.

Cons: two flashcards asking essentially the same thing in slightly different wording ("What is price elasticity?" vs. "What does price elasticity mean?") would both survive an exact-text check as "different," even though showing a student both is just noise, not two distinct pieces of learning.

What would actually change in the code: pipeline._is_duplicate and its use of difflib.SequenceMatcher would be replaced by a plain == string comparison — less code, but measurably worse at catching the kind of near-duplicate that actually shows up in practice.

How the checklist UI actually gets its updates

While "Generate study material" is running, the student watches a checklist of topic names turn green one at a time. That update doesn't come from the UI polling the database or watching for new rows — the Pipeline is handed a simple callback function (progress_cb) when it starts, and calls it directly, by name, at specific points (right after a concept's quiz has been saved: report(f"Completed: {name}")). app.py supplies a function that updates the checklist display; the Pipeline itself has no idea what that function actually does with the message — it just calls it.

Alternative not picked: have the UI poll the database for progress instead

Pros: the Pipeline wouldn't need to know or care about progress reporting at all — total separation of concerns.

Cons: polling means picking an interval (too slow feels laggy, too fast wastes work re-querying a database that usually hasn't changed) and still needing a way to know when a concept is "fully done" versus "summary saved but flashcards not yet" from the data alone — extra inference the callback approach avoids entirely by just saying so directly, at the exact moment it's true.

What would actually change in the code: the progress_cb parameter would disappear from every function signature in the Pipeline and the agents, and app.py would instead need a timer-driven loop querying db.list_concepts repeatedly during generation, inferring progress from concept status values instead of being told directly.

Why the remediation loop reuses the Pipeline's own dedup code instead of having its own

_is_duplicate and _normalize (the similarity-check logic above) are defined in pipeline.py but imported and used by adaptive_loop.py too. A drill flashcard generated during remediation needs to be checked against existing flashcards using exactly the same rule a freshly-generated flashcard is checked against during normal generation — if the two used slightly different logic, a card could be treated as "new" during remediation but would have been rejected as a duplicate during normal generation (or vice versa), an inconsistency with no good justification.

Alternative not picked: give the remediation loop its own separate copy of the dedup logic

Pros: the two modules would be fully independent — a change to one could never accidentally affect the other.

Cons: "fully independent" here just means "two copies of the same rule that can silently drift apart" — a future bug fix or threshold tweak applied to one copy and forgotten in the other would reintroduce exactly the inconsistency described above, quietly, with no error to signal it happened.

What would actually change in the code: adaptive_loop.py's from services.pipeline import _is_duplicate, _normalize import would be replaced with its own separately-defined (and separately-maintained) copies of both functions.

6 The verification system

Two separate quality-control mechanisms exist in this app, and they catch genuinely different things. This section covers both in full: the similarity check that catches repeats, and the Verifier agent that catches wrong or mislabeled content. They're unrelated in how they work (one is plain code with no AI involved, the other is a real second AI model) but both exist for the same underlying reason — don't just trust the first thing generated.

How the similarity check actually works

The dedup logic (Section 5) doesn't check whether two flashcards are exactly the same text — it checks how similar they are, using a standard Python tool called difflib.SequenceMatcher. Here's concretely what that means, not just the name of the tool:

SequenceMatcher takes two pieces of text and finds the longest stretch of characters they have in common, then keeps looking for more matching stretches in what's left on either side of that first match, repeating until there's nothing meaningfully left to match. It adds up the total number of matching characters it found (call that M) and compares that to the combined total length of both pieces of text (call that T). The similarity score is 2 × M ÷ T — a number between 0 (nothing in common at all) and 1 (identical text).

What "0.75" actually means in practice. Before comparing, both pieces of text are first normalized — lowercased, and anything that isn't a letter, number, or space is stripped out (so punctuation and capitalization differences never count against similarity). Two normalized flashcard fronts scoring 0.75 or higher are treated as duplicates and the second one is discarded. Concretely: "what is price elasticity" vs. "what does price elasticity mean" share most of their words and letter patterns despite being worded differently, and land comfortably above 0.75 — correctly caught as the same underlying question asked two different ways. "what is price elasticity" vs. "what is supply" share far less (mostly just the generic "what is" opening) and land well below it — correctly kept as two distinct cards.

Why 0.75 specifically, and what moving it would actually do

A higher threshold (e.g. 0.9) would require near-exact text matches to count as duplicates — catching only the most blatant repeats, letting through more flashcards that ask essentially the same thing in noticeably different wording. More total flashcards survive, but more of them would feel repetitive to a student reading through the whole set.

A lower threshold (e.g. 0.5) would flag much more loosely related text as "duplicate" — risking rejecting two flashcards that are actually about genuinely different aspects of a topic just because they share a lot of common words (two cards both starting with "Explain how..." about two different mechanisms, for instance). Fewer total flashcards would survive, some of them wrongly discarded.

0.75 sits deliberately in between — high enough to avoid punishing two flashcards for merely sharing a topic and some vocabulary, low enough to actually catch genuine near-duplicates reworded differently. This same threshold, and the same underlying check, is also reused by export_builder.py when it merges the standalone Glossary view (Section 10) — one number, defined once, used everywhere something needs "are these two pieces of text basically the same thing."

The Verifier agent, in full

Once something survives shape-filtering (Section 5) — so it's already known to be well-formed — it goes to the Verifier for the check that actually matters: is it true, and is it about the right topic. This is a real second AI call, not a rule-based check.

The mechanism. Every surviving flashcard or quiz question for one concept is numbered and sent to Groq in a single batch, along with the concept's name and its grounding text (Section 5). The prompt asks Groq to judge each numbered item against two separate questions at once:

  1. Grounded — is this clearly supported by the notes (not invented, not contradicting them)?
  2. On-topic — is this actually about the stated concept, not some different topic that happens to also be true and grounded?

Groq returns one verdict per numbered item (valid or not, plus a short reason), and an item must pass both checks to survive — failing either one is enough to get it discarded.

What's actually happening underneath that judgment

This is a genuinely different kind of mechanism from the similarity check above, and worth being precise about the difference. The dedup check is a fixed formula — 2 × M ÷ T — that produces the exact same number every single time for the same two pieces of text, and you could compute it by hand. The Groq verification check has no formula at all. There's no score, no threshold, no calculation happening anywhere. Groq is simply given the notes and the item as plain text in the same request, and asked to output a plain yes/no judgment — "valid": true or false — based on its own trained language understanding, the same way it would answer any other question put to it in plain English.

Concretely, what "reading for groundedness" means for a language model: the notes text and the item being checked both sit in the same context the model reads before answering — there's no separate lookup or search step, no keyword matching happening behind the scenes. The model reads the notes the way it would read any passage, forms an internal understanding of what claims that passage actually supports, then reads the flashcard or quiz item and judges whether its claim is consistent with what it just understood the notes to say. This is the same underlying skill a language model uses for ordinary reading comprehension — "does this statement follow from this passage" — just pointed at fact-checking instead of, say, summarizing.

"On-topic" is judged the same way, just comparing against the concept name instead of the notes. The model reads the item's actual subject matter — what is this flashcard or question fundamentally about — and compares that against the concept name it was given, asking essentially "is what this item is testing the same thing as what this concept name refers to." Both checks are genuinely the same kind of operation: comparing the meaning of two pieces of text and judging whether they line up, in one case against the notes, in the other against a topic label.

This means the check is a judgment call, not a guarantee — and it isn't strictly one-item-at-a-time either

Because there's no formula, there's no way to audit why Groq decided an item was valid or invalid beyond the short "reason" string it's asked to return — unlike the dedup check, this judgment can't be independently recomputed or double-checked by hand, only trusted or not. It's also worth being honest that all of one concept's items are judged together in a single request, not truly in isolation from each other — the model reads the whole batch of numbered items at once and returns verdicts for all of them together, so in principle its judgment on item 3 is formed in a context that also includes items 1, 2, and 4, even though each verdict is nominally "about" just its own numbered item. This is the real, unavoidable tradeoff of using a second AI model as a check instead of a deterministic rule: it can catch things a formula never could (genuine factual or topical mismatches), but it inherits all of an LLM's usual limitations — it can occasionally be wrong, and asking it twice isn't guaranteed to produce the identical verdict both times.

Why the on-topic check exists at all — a real bug, not a hypothetical

Earlier in this project, the Verifier only checked groundedness. That let a real, specific failure slip through: asked to write quiz questions for a concept the notes barely covered (or didn't cover at all — a manually-added concept), the generator would sometimes fall back to writing real, true, well-grounded questions about a different topic the notes covered well instead — questions that were entirely factually correct and genuinely supported by the notes, just filed under the wrong concept's quiz. A pure groundedness check has no way to catch that, because the content genuinely was true and grounded — it just wasn't about what it claimed to be about. Adding the second, independent relevance check specifically closed that gap.

Why this runs on Groq, specifically, not Gemini

Covered briefly in Section 2 as a tech-stack choice; the reasoning is worth restating here as a verification-design decision on its own terms. If the same model that wrote a flashcard is also the one asked "is this correct?", a systematic blind spot in how it reasons about the topic is likely to be present both times — it's checking its own instinct against itself. A genuinely different model, from a different company, trained differently, is much less likely to share that exact blind spot. That's the entire justification for spending a second, separate API integration on this rather than just asking Gemini to check its own work with a different prompt.

"Fails open" — what happens when the Verifier itself can't run

If the Groq call fails outright (rate limit, network issue, Groq's own service being briefly unavailable), verify_items doesn't crash the generation run or block on retrying indefinitely — it logs a warning and returns an empty result list, which every caller treats as "nothing came back verified, so let the content through unverified" rather than "treat everything as rejected."

Alternative not picked: "fail closed" — if verification can't run, reject everything

Pros: a stricter safety guarantee — nothing unverified ever reaches the student, no exceptions.

Cons: the Verifier is a quality check layered on top of content that already passed shape/type filtering (Section 5) — it's a second opinion, not the only thing standing between the student and completely fabricated content. Treating a temporary Groq outage as a reason to discard an entire concept's already-shape-valid flashcards and quiz (or to make the whole generation run fail) would punish the student for an availability problem on a third-party service that has nothing to do with whether the content itself is actually fine.

What would actually change in the code: the except Exception: block in verify_items that currently logs a warning and returns [] would instead re-raise the error (or return a result that marks everything invalid), and every caller in pipeline.py/adaptive_loop.py would need its own handling for "an entire concept's content generation just failed because a third-party verification service was briefly down" — a much harsher failure mode for a problem that's usually temporary.

Why the notes get truncated to 8,000 characters for this specific call

Every other place in this app that sends notes to an AI model truncates to 20,000 characters. The Verifier truncates to a noticeably smaller 8,000. This isn't an oversight — Groq's free tier caps the specific model used here at a fairly tight number of tokens processed per minute, and a single verification call already includes the numbered items being checked plus the notes as context. Keeping the notes slice smaller here specifically is what keeps one verification call from eating too much of that shared per-minute budget on its own, leaving room for the other verification calls that need to happen in the same generation run (recall from Section 4: a typical 8-concept document makes 16 separate Groq calls, two per concept, all competing for that same tight per-minute allowance).

7 The PYQ subsystem

This is the single most heavily reworked part of the whole app — the feature that took the most real iteration, dead ends, and evidence-gathering to get right. It's worth walking through not just what the final design is, but what was tried and rejected along the way, because the reasons those attempts failed are as instructive as the final answer.

Two distinct jobs, bookending the main pipeline

PYQ Solver does two genuinely separate things, already traced in Section 4: reading the questions off an uploaded paper (extraction — turning a photo or document into a clean list of question text), and writing a model answer to each one (solving). Extraction happens before the main Orchestrator → Summarizer → Flashcard Maker → Verifier → Quiz Maker → Verifier sequence even starts (the extracted question text becomes the "notes" fed into that sequence); solving happens only after that entire sequence finishes, once real concepts exist for answers to be matched against.

Marks capture, and why marks beats Depth as the length signal

When a question paper is read, the extractor doesn't just pull out question text — it captures each question's stated marks weight too (parsing something like "(10 marks)" or "[5]" off the page and separating it from the clean question text). This turned out to matter a lot, because Depth alone wasn't a reliable way to decide how long a given answer should be.

The concrete evidence. Two real questions, both genuinely worth 10 marks, were tested side by side under the earlier design. One named four distinct sub-parts (a Macro Market / Micro Market / Macro Industry / Micro Industry framework question) and produced a long, well-developed answer. The other named only two sub-parts ("support your answer using any two of these models") and, under the same 10-mark weight, came out barely a third as long. Same marks, wildly different length — purely because length was being driven by how many parts the question happened to name, not by how much the question was actually worth. Marks weight doesn't have that problem: it's a number stated on the page, independent of how the question happens to be phrased.

Three length-control attempts that failed

Getting from "answers are too short" to the current design took three rejected approaches first, each defeated by the same underlying problem:

  • A raw word-count target ("write at least 600 words") — the model would satisfy the number with padding, repetition, or generic restatement rather than genuinely writing more substance.
  • A required paragraph count ("write at least 4 paragraphs") — trivially satisfiable by writing four short, thin paragraphs instead of one thin one; the count went up, the actual depth didn't.
  • A sentences-per-paragraph minimum ("each paragraph must have at least 4 sentences") — closer, but still just another number for the model to satisfy the letter of without necessarily satisfying the intent; a model can write four short, low-content sentences as easily as four substantive ones.

The pattern underneath all three failures: a small, fast model (Section 2) can reliably satisfy a count without the human intent behind that count actually being met, because counting is a much easier task for it to game than genuinely reasoning about whether it has said enough.

What actually worked: forcing content, not count

The fix that held up under testing was to stop asking for a length at all and instead name the specific content every developed point in a high-mark answer must contain — content the model can't fake without actually engaging with it:

  1. A precise definition of the concept, including what it's typically measured or evaluated against.
  2. How it specifically applies here, referencing at least one concrete detail from the actual question or scenario — not a generic restatement.
  3. A second, hypothetical or illustrative example beyond the scenario itself.
  4. A comparison or contrast with a related, adjacent idea.
  5. A specific risk, limitation, or open question relevant to that point.
  6. A closing line on why that point matters for the overall outcome.

A model can pad a word count or split one idea into four thin paragraphs; it's much harder to fake "here is a second, different, concrete example" or "here is a genuine contrast with a related idea" without actually producing one. This — combined with the thinking budget described below — is what finally produced answers with real, verifiable depth instead of length that only looked like depth.

The marks-to-minimum-points table

How many of those fully-developed points a high-mark answer needs is set directly by marks weight, in brackets, and deliberately does not depend on how many sub-parts the question happens to name:

If a question names fewer parts than its marks bracket requires — the "any two models" 10-mark example above only explicitly named two — the model is instructed to derive additional genuinely relevant angles of its own (an additional applicable model, a cause, an underlying mechanism, a further consequence) to reach the required minimum, rather than stopping short because the question's own wording under-specified how many parts to cover. This is exactly what fixed the two-real-10-mark-questions inconsistency described above.

Thinking budget

Gemini supports an optional setting that lets it reason internally before committing to its final written answer, instead of writing linearly from the first word and never revising course. This app only turns that on for PYQ answers that actually need real depth (marks 7+, or an unmarked question at Deep dive) — never for the high-volume calls (concept summaries, flashcards, quiz questions across every concept in a document), because reasoning first adds real latency, and for those simpler, high-volume calls that latency isn't worth paying on every single one of the dozens of calls a normal document generates (Section 4's roughly-40-call tally).

Solo calls vs. batched calls — and a discovery about prompt placement, not just wording

Short, low-mark questions get batched together (up to 4 per call) into one request, each tagged inline with its own required length. Any question substantial enough to need the content-forcing treatment above is instead solved completely alone, in its own dedicated call, with its own separate, more spacious prompt.

Why solo, given batching saves API calls. The reason isn't just about avoiding a long answer getting cut short by a shared response — it's a genuine, measured discovery about how much weight a model gives an instruction based on where in the prompt it physically sits. The exact same length/depth instruction, tested side by side, produced roughly twice the output when it stood as its own prominent paragraph in a dedicated prompt, compared to being embedded inline inside a numbered multi-question list alongside a marks tag. Same wording, same model, same content requirements — moving it to a more prominent position in the prompt measurably changed how seriously the model treated it. That's why a substantial question gets an entirely separate prompt template, not just a longer allowance within the shared one.

A real bug: matching answers back to questions by position, not by trust

Solutions coming back from a solve call are matched to their original question text by their position in the list — first solution to first question, second to second — never by trusting whatever text the model itself echoes back into its own "question" field in the response. This was a deliberate fix for a real, observed bug: when a question was tagged inline with its marks and length instructions (the batched format above), the model sometimes echoed the entire tagged line back — numbering, bracketed instructions and all — into what was supposed to be just the clean question text, polluting what got shown to the student and stored in the database. Matching by position instead of trusting the model's echo makes that entire category of bug impossible, regardless of what the model does with the "question" field.

The hint-expansion feature, and the design journey behind its 700-word ceiling

Once an answer exists, "Expand answer" lets a student pull more material out of its "to go further" hints — a genuinely separate follow-up call that appends new content to the existing answer and produces a fresh set of hints for what's still missing. Getting the limit on this right took real back-and-forth, worth walking through because the first two ideas both had real, specific flaws:

  • First idea: a fixed number of clicks, computed once from the question's starting marks. A 2-mark question would get more allowed expansions than a question that started at 10 marks, on the reasoning that it had further to climb. This fell apart once expansion length itself became content-driven rather than count-driven (the same lesson from earlier in this section): a single click on a question with unusually rich hints could jump straight past a thousand words, and a fixed click-budget computed in advance has no way to notice that already happened — it would keep offering more rounds regardless of how large the answer had already grown, defeating the entire point of having a ceiling.
  • Fix: check the actual result after every expansion, not a plan made in advance. The ceiling that actually shipped is much simpler than either previous idea: after every expansion call returns, the code measures the real word count of the resulting answer, in plain code, no AI involved. If it's at or past 700 words, the fresh hints the model returned are discarded outright regardless of what they say — which is what makes the "Expand answer" button disappear on the next render. If it's still under, the button and a new set of hints stay available. Nothing here is decided in advance or trusted to the model's own judgment about when to stop — it's a direct, external measurement taken after the fact.

The 700-word number itself isn't arbitrary — it comes directly from what a genuinely thorough, fully-developed 10-mark answer using the content-forcing approach above actually measured out to during testing, with some headroom added for normal run-to-run variance in how much the model produces for the same prompt.

8 The adaptive remediation loop

Everything up to this point (Sections 4-7) is about the first pass — generating a document's summaries, flashcards, quiz, and PYQ answers once. This section covers what happens after that, when a student actually takes a quiz and does badly on a specific concept. It's a genuinely separate mechanism from the main pipeline, living in its own file (adaptive_loop.py), reusing several of the main pipeline's pieces rather than reinventing them.

What actually triggers it

This is not a scan that runs automatically after generation, and it does not look at the whole document at once. It's reactive and per-concept: it only fires after a student has taken a quiz on a specific concept and submitted answers, and only for that one concept.

The exact condition. A concept is flagged "weak" only when both of these hold at once: the student got at least 2 questions wrong on it, and at least half of the questions they answered on it were wrong. Neither number alone is a reliable signal — a flat "2 wrong" would flag a student who answered 10 questions and got 8 right just as harshly as one who answered 2 and got both wrong, and a flat percentage alone breaks down at very low question counts (getting the single question you answered wrong reads as "100% wrong," which isn't meaningful evidence of a real gap). Requiring both together is what keeps the trigger from firing on noise.

When one or more concepts meet that bar, the UI shows a "Fix weak topics now" button rather than remediating silently in the background — the student sees which concepts were flagged and chooses to spend the extra generation time on them, instead of it happening automatically without their say.

Alternative not picked: an automatic quality pass over the whole document right after generation

Pros: would catch weak coverage immediately, without needing to wait for a student to actually struggle on a quiz first.

Cons: there's no reliable signal for "weak" until a student has actually attempted questions on a concept — before that, every concept looks the same (a summary, some flashcards, a quiz), and there's no evidence yet of which ones are actually hard to grasp for this specific student. Weakness here is defined by a real person's real wrong answers, not by anything inspectable in the generated content itself.

What would actually change in the code: there'd need to be some other quality signal computed from the content alone (verification failure rate per concept, maybe, or flashcard count falling short of the requested number) to decide what counts as "weak" without quiz data — a fundamentally different, and much less trustworthy, definition of the problem being solved.

What one remediation round actually does, step by step

Once triggered for a concept, run_remediation runs four steps in sequence, all for that one concept only:

  1. Re-explain. The Summarizer agent is called again, but not from a blank slate — it's given the concept's original summary (or, on a later attempt, the most recent remediation's summary) plus, if the student just got questions wrong, the specific misconception notes attached to those wrong answers. This lets the new explanation target the actual gap that shows up in this attempt, rather than generating a generic "different angle" on the same material blind. Critically, this new explanation is stored as its own separate database row, not overwritten on top of the original summary — both stay visible, each labeled by attempt number, so a student (or a professor) can see the concept's remediation history rather than just its final state.
  2. Drill flashcards. The Flashcard Maker is called again for just this concept, grounded in the notes plus the freshly-generated re-explanation (the same grounding-text pattern from Section 5) — so a drill card can draw on ground truth the original notes never stated, if the re-explanation is what actually made the idea click. The existing flashcards for this concept are passed in explicitly so the model knows what's already been asked and can genuinely produce new angles instead of near-restatements.
  3. Reschedule for review. This concept's existing flashcards are pushed back to the earliest position in the spaced-repetition schedule ("box 1"), the same review-scheduling mechanism used elsewhere in the app — a concept the student just got wrong is due for review again soon, not left on whatever later schedule it had drifted to before the wrong answers.
  4. Follow-up quiz. The Quiz Maker is called again for just this concept, on the same combined grounding text as the drill flashcards, producing a fresh set of questions the student can retake to show the gap has actually closed.

Reuse, not reimplementation, of the two-layer defense from Sections 5 and 6

Remediated content isn't treated as a special, lower-scrutiny case. The drill flashcards go through exactly the same shape-filtering (well-formed front/back text, not a stray JSON blob) as first-pass flashcards, then the same real Verifier call checking groundedness and on-topic relevance, before being kept. The follow-up quiz questions go through the same shape check (a real question, a real options list, a valid correct-index) and the same Verifier call. Nothing about being a "second attempt" earns content a pass on the checks that first-pass content has to clear.

Reuse of the dedup logic from Section 6 — and why it checks against everything, not just this concept

New drill cards are run through the identical similarity check from Section 6 — the same 2 × M ÷ T formula, the same 0.75 threshold — via the exact same underlying function the main pipeline uses, imported directly rather than copied or reimplemented. The one deliberate difference: a drill card is compared for duplicates against every flashcard already in the whole document, not just the ones belonging to this concept. That's a small but intentional choice — a re-explanation drawing on fresh grounding text could plausibly produce a card that overlaps with something already covering a related idea elsewhere in the document, not just within this one concept's existing cards, so the dedup check is scoped to catch that too.

The stopping condition — a hard cap, then an honest handoff

Each concept tracks its own attempt count, and remediation is capped at 3 attempts. This isn't a diminishing-returns heuristic trying to detect when progress has stalled — it's a flat, simple ceiling, on purpose: there's no reliable automated way to judge from the generated content alone whether a fourth AI-written explanation would actually help a student who hasn't grasped a concept after three genuinely different attempts, so the app doesn't pretend it can measure that and keep looping.

Once the cap is reached, the app does one more useful thing before giving up: it makes a single dedicated Gemini call asking, in effect, "does this concept depend on some simpler, more foundational idea also present in these notes?" If the model identifies a plausible prerequisite the student hasn't been explicitly taught yet, that's surfaced to the student as a specific, actionable suggestion (and the concept is flagged rather than silently left as "still learning"). If no clear prerequisite is found, the concept is flagged with an honest message recommending the student fall back to a human resource — their instructor, a textbook, a study group — rather than the app continuing to throw more AI-generated text at a gap it has already tried three times to close.

This handoff is a real, deliberate limit on what the app claims to do

The app never claims that three attempts will fix any given misunderstanding, and it isn't trying to. Some gaps genuinely need a human explaining things a different way, or noticing something about how a specific student is thinking that a re-explanation prompt has no way to observe. The cap exists specifically so the app says that honestly at a known point, instead of generating a fourth, fifth, sixth explanation indefinitely on the unfounded hope that eventually one will land.

9 The data model

Everything the pipeline generates and every quiz attempt a student makes ends up in one local SQLite file (data/studymate.db). This section walks through the seven tables that make up the schema, why each one is shaped the way it is, and why SQLite specifically was the right tool for storing all of it.

The seven tables, as a dependency tree

Rather than list the tables flat, it's clearer to see them as a tree rooted at one document:

  • documents — one row per uploaded notes-set or PYQ paper. Stores the raw uploaded text itself (raw_text), plus the two settings chosen once up front and never changed mid-run (Section 4): explanation_style and depth_level.
  • concepts — one row per topic within a document, referencing documents.id. This is the real unit of work everywhere else in the schema hangs off of.
    • flashcards — reference concepts.id. One row per card.
    • quiz_questions — reference concepts.id. One row per question, with options and distractor_notes (the misconception-per-wrong-option map from Section 6) stored as JSON text inside a TEXT column, not as their own tables.
    • concept_remediations — reference concepts.id. One row per remediation attempt's re-explanation (Section 8).
    • quiz_attempts — reference both quiz_questions.id and concepts.id directly (a small deliberate denormalization, covered below). One row per single answer a student submits.
  • pyq_solutions — references documents.id directly, sitting outside the concept tree entirely (also covered below, with the reasoning).

Why options and distractor_notes are JSON-in-a-column rather than their own tables (an options table with a foreign key back to the question, say): a quiz question's options are never queried, filtered, or updated independently of the question itself — they're always read and written as one unit, alongside the question they belong to. A separate table buys relational flexibility (querying "which options exist across all questions") that this app never needs, at the cost of an extra join on every single quiz read. Storing them as a JSON blob in one column is the simpler choice that exactly matches how the data is actually used.

concepts.source: auto vs. manual

A concept row can come from two places — extracted automatically from the uploaded notes during the main pipeline run, or added manually by the student afterward (a topic they know is on the syllabus but that the notes didn't cover). This single text field is the entire mechanism that makes manually-added concepts work at all: nothing downstream — flashcard generation, quiz generation, verification, remediation — branches on this field or treats a manual concept specially. They all just call the same functions with whatever grounding text is available (Section 5's grounding-text pattern: notes plus the concept's own generated summary), and for a manual concept where the notes say nothing, that pattern is what supplies real grounding anyway, since the concept's own summary still gets generated and stored regardless of where the concept came from.

concepts.status: a small lifecycle state machine

Each concept moves through four states over its lifetime: unseen (generated, not yet quizzed) → learning (the student has taken at least one quiz attempt, possibly been through remediation) → either cleared (the student answered correctly and the concept is considered understood) or flagged (Section 8's remediation cap was reached, or a prerequisite gap was surfaced, without the concept clearing). This status field is what drives what the UI shows for a concept — whether to offer a quiz, show a "weak topic" prompt, or show the honest handoff message — and Section 8's run_remediation / clear_concept_if_correct functions are the only things that ever move a concept out of learning.

Spaced repetition: box_level and next_review_at

Flashcards use a Leitner-system schedule — a well-known spaced-repetition idea where a card lives in one of several numbered "boxes," and which box it's in decides how soon it's due for review again. Every new card starts in box 1. A correct review moves it up one box (capped at box 5); an incorrect one drops it straight back to box 1, regardless of what box it was in before. This is also the exact mechanism Section 8 leans on: when a concept is flagged weak, every one of its flashcards is pushed straight back to box 1 (reschedule_flashcards_for_concept(concept_id, correct=False)) — due for review immediately, on the reasoning that a concept the student just got wrong on a quiz needs its flashcards revisited soon, not whenever their existing box happened to schedule them next.

Alternative not picked: no spacing, just "review daily" or "review in order"

Pros: far simpler — no box_level column, no interval table, no reschedule logic; every card just shows up on some fixed rotation regardless of how well the student already knows it.

Cons: wastes a student's review time on cards they've already clearly mastered, at exactly the same rate as cards they keep getting wrong — the entire point of spaced repetition (a genuinely well-evidenced learning technique) is to spend more review time where it's actually needed and less where it isn't.

What would actually change in the code: the flashcards table would drop box_level and next_review_at entirely, reschedule_flashcards_for_concept and LEITNER_INTERVALS_DAYS would disappear, and whatever UI shows "cards due for review" would instead just show all cards, or all cards in creation order — a noticeably less useful study tool for the same amount of generated content.

Why remediation history is its own table, not an overwrite

concept_remediations exists specifically so that re-explaining a concept (Section 8, step 1) never destroys the original explanation — each attempt's re-explanation is inserted as a new row, tagged with its attempt number, and the original concepts.summary is left untouched underneath all of them.

Alternative not picked: just overwrite concepts.summary on each remediation

Pros: one fewer table, simpler reads — there's only ever one summary to fetch per concept, no need to pick "the latest one."

Cons: loses the concept's actual learning history. Being able to show a student (or a professor evaluating the project) "here's the original explanation, here's attempt 2, here's attempt 3, and here's what changed each time" is a genuinely useful, honest record of what the adaptive loop actually did — an overwrite-in-place design would silently discard that the moment a second attempt happened, leaving only the most recent explanation with no trace that earlier ones ever existed.

What would actually change in the code: add_concept_remediation would become an UPDATE concepts SET summary=? WHERE id=? instead of an INSERT into a separate table, and the concept_remediations table and every place that reads "prior remediations" (Section 8's run_remediation, which pulls the most recent one to ground the next re-explanation) would need a different way to access what the previous attempt actually said.

flashcards.source / attempt, and what quiz_attempts is actually for

flashcards.source (generated vs. drill) and flashcards.attempt (0 for an original card, the remediation attempt number for a drill card) together record exactly where every flashcard came from — the main pipeline's first pass, or which specific remediation round produced it — without needing a separate table just to track flashcard provenance.

quiz_attempts is the raw evidence table everything in Section 8 is actually computed from. Every time a student answers one quiz question, one row is inserted recording which question, which concept, which option they picked, and whether it was correct. Section 8's is_weak check — "at least 2 wrong and at least half of answered questions wrong" — is computed directly by counting rows in this table per concept, not from some running tally kept elsewhere; the wrong/answered counts the UI shows and the remediation trigger reads off of are both derived fresh from this same table each time. Keeping every individual attempt as its own row (rather than, say, just a running "times correct / times wrong" counter on the concept) is also what lets the misconception notes get pulled back out for a specific wrong attempt when triggering remediation (Section 8's wrong_misconceptions list) — a running counter would have thrown that detail away the moment it was rolled up.

Why SQLite, specifically, for this project

Briefly touched in Section 2 as a tech-stack line item; here's the fuller reasoning as a data-model decision on its own terms. SQLite stores the entire database as one ordinary file on disk, needs no separate server process running, and Python's standard library talks to it directly (import sqlite3) with no extra service to install, configure, or keep alive. For a single-user MBA coursework project that runs locally and was never going to serve concurrent users across a network, that's a very close match to the actual requirements — the data still needs real structure (foreign keys, typed columns, the ability to query "all flashcards due for review across a document" efficiently) that a much simpler option like flat JSON files on disk wouldn't give for free, but it doesn't need anything close to a client-server database's concurrency handling.

Realistic alternatives, and why each was passed over

Flat JSON files (one file per document, holding all its concepts/cards/questions nested inside) — the simplest possible option, and genuinely tempting for a small project. Rejected because several real operations get much harder without a real query layer: finding "all flashcards due for review today across every document," or "every quiz attempt for this concept," would mean loading and manually scanning whole JSON structures in Python instead of a single indexed SQL query — workable at a handful of documents, but a noticeably worse fit even at the scale a semester of coursework realistically produces.

A client-server database (PostgreSQL, MySQL) — real concurrency handling, real production scalability, the kind of database an actual multi-user product would need. Rejected because it needs a separate server process running somewhere, real setup (installing the server, managing credentials, connection pooling), and buys concurrent-multi-user correctness this project has no user for — a single student, running the app locally, is never writing to the database from two places at once. All of that operational weight would be pure overhead here.

What would actually change in the code: against Postgres, services/db.py would swap sqlite3.connect(DB_PATH) for a connection string and a real client library (psycopg2 or similar), get_conn() would need real connection pooling instead of opening and closing a lightweight file connection per call the way it does now, and the app would need a running database server as a deployment dependency it doesn't have today. Against flat JSON, every function in db.py that currently runs a SELECT with a WHERE/JOIN would instead need to load a file (or several) into memory and filter with Python list comprehensions by hand.

Schema evolution: _migrate() instead of a migrations framework

The schema has changed more than once since the project started (adding explanation_style/depth_level to documents, adding source/attempt to flashcards, for instance), and a developer's already-existing local studymate.db file needs to keep working after each change rather than needing to be deleted and recreated. init_db() runs the full CREATE TABLE IF NOT EXISTS schema unconditionally (a no-op against a database that already has those tables), then calls _migrate(), which checks each table's actual current columns via PRAGMA table_info and runs an ALTER TABLE ... ADD COLUMN only for whichever new columns aren't already there.

Alternative not picked: a real migrations framework (Alembic or similar)

Pros: versioned, reversible migrations, a real history of every schema change as its own file, the standard approach for a production codebase with a team of developers and real deployed databases to keep in sync.

Cons: genuinely disproportionate tooling for a project with one schema, one local SQLite file per developer machine, and no deployed database anyone needs to keep in sync with anyone else's. The hand-written additive-column check does exactly the one thing this project actually needs — don't break an existing local dev database when a column gets added — in about a dozen lines, with no new dependency and nothing to learn or configure.

What would actually change in the code: _migrate() and the inline PRAGMA table_info checks would be replaced by a directory of numbered migration scripts and a library managing which ones have already run against a given database — real infrastructure for a problem this project's actual scale doesn't have.

pyq_solutions: deliberately outside the concept tree

Every other generated content table hangs off concepts.id with a real foreign key. pyq_solutions doesn't — it references documents.id directly, and stores matched_concept as a plain text column, not a foreign key to an actual concept row. This is a direct consequence of how PYQ Solver actually produces that field (Section 7): the model is asked to name the closest-matching concept from the list it's given, as free text in its JSON response, not to return a concept ID it's confident is correct. Treating that as a real foreign key would claim a stronger guarantee than actually exists — that the label is guaranteed to correspond to some real row in concepts — when it's really just the model's best-effort text label, useful for display ("this answer relates to: Price Elasticity") but not something safe to build a strict relational constraint on top of.

A soft link, not a hard one — and that's the honest choice

If matched_concept were a real foreign key, a PYQ solution whose model-named concept didn't exactly match any real concept row (different capitalization, a slightly different phrasing) would either fail to insert outright or need extra normalization/fuzzy-matching logic just to satisfy the constraint. Keeping it as plain text sidesteps that entirely, at the honest cost that the schema itself can't guarantee matched_concept actually refers to something real — any code that wants to cross-reference a PYQ solution back to a concept has to do its own best-effort text comparison, not a guaranteed join.

10 The export system

Everything so far lives inside the running app — Streamlit, the SQLite file, an active Python process. This section covers the one part of the app deliberately designed to leave all of that behind: the "Download as HTML" / "Download as PDF" buttons, which turn a document into a single file a student can save, email, or open on a completely different machine with nothing installed.

What "export" actually means here: a fully self-contained artifact

The exported HTML file isn't a link back into the running app, and it isn't a folder of separate assets (a stylesheet here, a script there, images elsewhere) — it's one file, with its CSS and JavaScript embedded directly inside it, that works completely offline. Open it by double-clicking, no server, no internet connection, no Python, no dependency on the SQLite database it came from still existing. This matters specifically because the running app itself has none of those properties: it needs Streamlit running, a live local database file, and effectively one machine — none of which a student can hand to a study group or open on a phone that never had the project installed.

One shared assembly step, two different renders

export_builder.py's _build_context(document_id) is the single place that decides what goes into an export — every concept (with its summary and full remediation history), every flashcard, every quiz question, every PYQ solution, and the merged glossary (below). Both build_html and build_pdf call this exact same function and get back the exact same data; they only differ in which template they hand that data to and how they render it. This is a deliberate one-source-of-truth choice: if the HTML export and the PDF export instead each independently queried the database for what to include, they could quietly drift apart over time (one export format gaining a new field, the other not), with no single place responsible for "what does a study pack actually contain."

Why two export formats instead of one

An interactive HTML page and a static PDF solve genuinely different problems, not the same problem twice:

HTML export vs. PDF export vs. picking just one

HTML only: keeps the interactivity — flip-to-reveal flashcards, a self-graded quiz, theme and font controls — but can't be printed cleanly (click-to-reveal content is invisible on paper) and isn't the natural format for something a student wants to physically annotate or bring into an exam-prep session away from a screen.

PDF only: prints cleanly and works anywhere a PDF viewer exists (which is closer to universal than "a modern browser with JavaScript enabled"), but loses everything interactive — no flip animation, no self-quiz that grades itself, nothing dynamic. Every flashcard and quiz answer has to sit in plain view directly on the page.

Both, as built: the interactive study-and-review experience lives in the HTML export; the plain, printable answer key lives in the PDF export. Neither format is asked to do the job it's structurally bad at.

Jinja2's role: one-shot templating, not a live UI

Both templates are rendered with Jinja2 — Template(...).render(...) takes the Python dict from _build_context and substitutes it into the HTML template's {{ }} placeholders and {% for %} loops once, producing a finished, static block of HTML text that gets written straight to the download. This is worth contrasting directly with how the app itself is built: Streamlit (Section 11 covers this in full) re-executes the entire Python script from top to bottom on every single interaction, deciding what to show fresh each time. Jinja2 here does the opposite — it renders exactly once, at the moment "Download" is clicked, and everything after that (which page is showing, what theme is active, which quiz answer was picked) is handled entirely by the small hand-written JavaScript embedded in the file itself, with no Python involved at all once the download happens. An exported file has no Python runtime attached to it anymore — it can't rerun a script, so all of its interactivity has to be self-sufficient client-side JS, not more Streamlit.

The interactive HTML export's own mini front-end

The HTML export bundles a genuinely small but complete front-end of its own, entirely inside <script> tags in the same file:

  • Multi-page navigation — the exact same data-page attribute + .page.active CSS pattern this very architecture document uses (Section 4): clicking a nav link removes .active from every page and nav link, adds it to the clicked one, and scrolls to top. This app's own study-pack export was, in fact, the direct model this documentation site's own page-switching was copied from.
  • Flip-to-reveal flashcards — each card is a plain div with a front face and a back face stacked via CSS, and a single onclick="this.classList.toggle('flipped')" toggles which face shows. No JS framework, no state management — the class toggle and the CSS are the entire mechanism.
  • A self-graded, client-side-only quiz — every quiz question, its options, and its correct index are serialized once into a plain JSON blob (QUIZ_DATA) embedded directly in the page source. A small renderQuiz() function builds the quiz UI from that array and grades it entirely in the browser when submitted — no server call, no database write, because there's no server to call once this file is downloaded. A score the student gets from this exported quiz never makes it back into the app's own progress tracking (Section 9's quiz_attempts table) — it's a genuinely separate, disconnected copy of the quiz, useful for review but not wired into the adaptive loop.
  • Theme and reading-comfort controls — the same theme-switching pattern as this documentation site, plus sliders for font size and reading-column width, each applying a CSS custom property live as the slider moves.

Why every one of those settings is saved to localStorage, specifically. This file might be opened on a machine with no account system, no server, and — once downloaded — potentially no connection back to anything at all (a student could email it to themselves, or carry it on a USB drive). localStorage is the one persistence mechanism that needs absolutely nothing beyond the browser itself: no login, no network call, no server-side storage to provision. A returning visit to the same file on the same browser reloads the last theme and slider settings automatically, entirely because the browser remembered them locally — which is exactly the right amount of persistence for a file with no backend behind it at all.

The glossary merge, reusing Section 6's exact similarity check

Every concept keeps its own key terms in its own summary — including terms another concept also happens to use, which is normal (real topics genuinely share vocabulary) and not treated as a problem anywhere else in the app. The standalone Glossary view in the export is the one place that would actually look broken if the same term showed up twice, so _merge_glossary_terms runs a dedup pass only at export-assembly time, using the identical mechanism from Section 6: normalize each term (lowercase, strip non-alphanumerics), then compare with the same SequenceMatcher ratio at the same 0.75 threshold used for flashcard dedup — reusing the number and the formula rather than inventing a second one. This is a deliberate assembly-time-only fix: nothing about how concepts store their own key terms changes, only how the export flattens them into one shared list.

Why the PDF reveals every answer directly — not a "PDF-ified" copy of the HTML template

The PDF template is a genuinely separate file (pdf_template.html), not the interactive template rendered a different way. A printed page has no clicks, no hover, no JavaScript execution at all — "click to flip" simply cannot exist on paper. Rather than ship a broken, inert copy of the flip-card markup, the PDF template shows flashcard fronts and backs side by side in a plain table, and every quiz question with its correct answer printed directly beneath it, clearly labeled ("answers revealed") right in the export's own subtitle so there's no ambiguity about why nothing needs to be clicked.

xhtml2pdf as the PDF engine — the mechanism, and its real limitation

Touched briefly in Section 2 as a tech-stack line; here's the actual mechanism. xhtml2pdf's pisa.CreatePDF takes a plain HTML+CSS string — the same kind of string Jinja2 just rendered — and converts it directly into PDF bytes, entirely within the Python process, with no headless browser, no external binary, and no separate rendering service involved.

The real tradeoff: a much smaller CSS subset than an actual browser

What this buys: a pure-Python dependency (installed like any other pip package), no external Chrome/Chromium binary to bundle or manage, and a fast, simple, in-process conversion — well suited to a coursework project that shouldn't need a browser automation stack just to produce a PDF.

What it costs: xhtml2pdf only understands a meaningfully smaller slice of CSS than a real browser engine does — modern layout features (flexbox, grid, many CSS custom properties) aren't reliably supported. This is exactly why pdf_template.html is written as its own separate, deliberately simple template using plain tables and basic block layout, rather than trying to reuse the interactive HTML template's richer CSS and hoping xhtml2pdf renders it correctly — the PDF template is written for this specific renderer's real capabilities, not adapted after the fact from something else.

What would actually change in the code: the alternative with full modern CSS support is a headless-browser-based PDF tool (Playwright or a headless Chrome invocation) rendering the interactive HTML template itself and printing that to PDF — which would let the PDF and HTML templates converge into one file, at the cost of bundling and managing an entire browser binary as a project dependency, for a coursework app that doesn't need that level of fidelity.

11 The Streamlit interaction model

Several things earlier in this document were explained by pointing forward to "Streamlit's execution model, covered fully in Section 11" — why the pipeline is fully sequential (Section 4), why generation is one single blocking step (Section 4), why the busy overlay exists at all. This section is where all of that actually gets explained, from the ground up: what Streamlit fundamentally is, and every consequence that follows from it mechanically.

The one fact everything else in this section follows from

What it is. Streamlit is not a typical web framework with routes, request handlers, and a server-side app object that persists between requests. A Streamlit app is a single Python script (app.py, in this project) that Streamlit re-executes from the very first line to the very last line, every single time something happens in the browser — a button click, typing into a text box, selecting a dropdown option, or an explicit st.rerun() call from the code itself. This full top-to-bottom re-execution is called a "rerun," and it is the single fundamental fact Streamlit is built around.

Why it works this way. Streamlit's whole pitch is that a developer writes plain, linear, top-to-bottom Python — no callback functions to wire up for every widget, no explicit "update this part of the page" logic to write by hand. The tradeoff for that simplicity is that the framework achieves it by just running the entire script over again and using each rerun's output to redraw the page. There's no partial-update model by default — the entire script's control flow is what decides what widgets and content exist on a given rerun.

What this means concretely. Every plain Python variable declared in app.py — a list, a counter, a flag, the result of an earlier calculation — is thrown away and rebuilt from scratch on every rerun, exactly as if the script had never run before. Nothing survives a rerun except what is explicitly stored in st.session_state — a dictionary-like object Streamlit itself keeps alive across reruns, tied to one browser tab's session. If a value needs to persist across an interaction — which document is currently selected, whether a long-running generation is in progress, what a student answered on a quiz question before submitting — it has to live in st.session_state, on purpose, or it's gone the instant the next rerun starts.

Why the pipeline is fully sequential — the actual mechanism, not just the conclusion

Section 4 already stated that nothing in this app runs in parallel and pointed here for the reason. Here is the actual mechanism: a rerun-driven script has no natural, safe place to keep a background thread or an async task alive across reruns without deliberately-built extra machinery (a thread-safe queue, a polling loop checking a shared variable, careful handling of Streamlit's own threading model) — none of which this app has, because it was never asked to run two things at once. A single st.spinner(...) block wrapping a call to pipeline.generate_study_material(...) simply runs that Python function to completion, line by line, exactly like calling any ordinary function — there is no framework-provided way to fire off "start the Summarizer and the Flashcard Maker at the same time" from inside a rerun and have the script continue past that point before both finish. The single-threaded, one-agent-at-a-time pipeline design from Section 4 is therefore not just a design preference — it's the natural shape of what a plain function call inside one Streamlit rerun can actually do without extra infrastructure this project has no need for.

The click → flag → rerun → do-the-work pattern

"Generate study material," "Solve question paper," and "Fix weak topics now" all use the identical four-step pattern, and it's worth walking through exactly why each step exists rather than just what it does. Concretely, from the Generate button (app.py:353-359):

  1. gen_clicked = st.button(...) — st.button returns True only on the exact rerun where it was clicked. On every other rerun (including the very next one Streamlit triggers), it returns False again — a button's "clicked-ness" is not persistent state, it's a one-shot signal for a single rerun.
  2. if gen_clicked: st.session_state.generating_notes = True — because that one-shot signal is about to disappear on the next rerun, it's immediately converted into a durable flag in session_state, which — unlike the button's return value — will still read True on every subsequent rerun until something explicitly sets it back to False.
  3. st.rerun() — called immediately, before any of the actual slow work happens. This forces Streamlit to immediately restart the script from the top rather than falling through into the generation call on the same rerun that detected the click.
  4. On that next rerun, the script reaches if st.session_state.generating_notes:, sees it's True, and only then does the real work — parsing files, calling the pipeline, writing to the database.

Why split the click and the work across two separate reruns at all — why not just do the work directly inside the same if gen_clicked: block? Because Streamlit doesn't repaint the browser until the entire script finishes running top to bottom. If the actual multi-second pipeline call happened directly inside the same rerun that detected the click, the button would stay visually unclicked/unchanged in the browser for the whole duration of the call — no spinner, no disabled state, nothing — because none of that visual feedback gets sent to the browser until the whole script returns. Calling st.rerun() immediately after setting the flag forces an early, cheap rerun whose only job is to redraw the page with the flag now set — which is what makes the spinner and the disabled buttons (via the _BUSY flag, below) actually show up before the slow work starts, instead of after it finishes.

A real bug this pattern had to account for: Streamlit's own Stop control

Streamlit gives the user a native "Stop" control (a running-indicator with a stop icon) while a script is executing, and clicking it raises StopException inside the running script to actually interrupt it. The flag-reset code (st.session_state.generating_notes = False) deliberately lives in a finally block, not after a plain try/except Exception. The reason: StopException is a BaseException, not an Exception — a plain except Exception: clause does not catch it, so it would skip straight past the reset code entirely, permanently leaving generating_notes stuck at True and the Generate button disabled forever on every future rerun, with no way for the student to recover except manually clearing browser state. finally is the one block Python guarantees runs even when an exception it doesn't catch is propagating through — which is exactly the guarantee needed here.

The busy overlay: why a plain spinner wasn't enough

The problem a bare st.spinner() has. st.spinner("...") shows a small animated message and visually dims the area around it, but it does not disable or intercept anything else on the page. While a generation call is running, every other button, upload widget, and input on the page is still fully live and clickable underneath that spinner. Clicking something else mid-generation doesn't error out cleanly — it queues up as a fresh interaction that Streamlit will process once the current script run finishes, producing confusing, out-of-order behavior (a second "Generate" click landing after the first one already started, for instance).

What was built instead. A full-page overlay — a fixed-position, semi-transparent div covering the entire viewport with a high z-index (999) and cursor: not-allowed — is rendered via st.markdown(..., unsafe_allow_html=True) whenever _BUSY is True. Because it's a real DOM element sitting visually on top of everything else on the page, it doesn't just look disabled — it physically intercepts every click that would otherwise land on a button or widget underneath it, so nothing can actually be clicked while it's showing, not just "shouldn't be."

The _is_busy() mechanism, and why it can't just check a fixed list of flags. (app.py:242-251) Three of the busy states are simple, fixed session-state keys (generating_notes, solving_pyq), and those get checked directly. But "Fix weak topics now" and "Expand answer" (the PYQ hint-expansion from Section 7) both use per-document or per-question dynamic keys — fixing_weak_{doc_id}, expanding_pyq_{...} — because multiple documents, or multiple PYQ answers, can each independently be mid-remediation or mid-expansion at once, and each needs its own separate flag rather than one shared boolean that would incorrectly report every document as busy just because one of them is. Since the exact key name for these depends on a database ID that isn't known in advance, _is_busy() can't just check st.session_state.get("fixing_weak_") — it has to iterate every key currently in session_state and pattern-match on the prefix (k.startswith("fixing_weak_")) to catch all of them regardless of which specific document or question they belong to.

Why Streamlit's own Stop control still has to stay clickable through the overlay

The overlay is deliberately built so Streamlit's native header — which holds the running-indicator and its Stop control — sits above the overlay in the page's stacking order, specifically because that Stop control is the only way to actually interrupt a stuck or too-long-running call. If the overlay covered the header too, a genuinely hung request (the retry-timeout ceiling from earlier sections caps most individual calls, but not every possible failure mode) would leave the student with literally no way to recover the page short of a full browser reload. The overlay's job is to block accidental double-clicks and out-of-order interactions on the app's own content, not to block the one legitimate escape hatch Streamlit itself provides.

The progress checklist: updating the page without a rerun

Section 5 mentioned the progress-callback mechanism briefly; here's the Streamlit-specific trick that makes it work. _make_progress_handler() (app.py:48-76) creates two st.empty() placeholders before the slow pipeline call starts, then returns a plain Python function (handle) that the pipeline calls directly, as a normal function call, once per concept as it works through the document. Each time handle is called, it doesn't return anything to trigger a rerun — it writes fresh Markdown straight into the existing checklist_box placeholder via checklist_box.markdown(...), which Streamlit is able to push to the already-rendered page immediately, without needing to finish the whole script and start a new rerun. This is the one place in the app that updates the visible page within a single rerun rather than needing a fresh one — because the pipeline call and the checklist update are both happening inside the exact same Python call stack, on the same script execution, just at different points in time as the loop over concepts progresses.

Each concept starts pending (⏳) the moment its generation begins and flips to done (✅) in place once the pipeline reports it finished — a genuinely different, more informative signal than a single status line that just gets overwritten with whatever concept is currently being worked on, because a growing checklist lets a student see the whole run's progress at a glance, not just "what's happening right this second."

Why the quiz uses st.form instead of the click-flag-rerun pattern

Every other interactive control in this app triggers an immediate rerun the instant it changes — a checkbox ticked, a dropdown changed. Left unmanaged, a multi-question quiz built the same way would trigger a full script rerun on every single radio button selection — pick an answer to question 1, the whole script reruns; pick question 2, it reruns again — which is both wasteful and visually disruptive (the page could jump or flicker between each pick).

st.form(key=f"quiz_form_{doc['id']}") (app.py:686-694) changes this: every widget declared inside the with st.form(...): block — each question's st.radio — stops triggering its own rerun the moment it's touched. Instead, all of the selections accumulate silently in the browser, and only st.form_submit_button("Submit quiz") actually triggers the rerun, at which point every widget's current value inside the form becomes available all at once. This is exactly the right fit for a quiz specifically because a quiz is naturally one atomic action from the student's perspective — "submit my answers" — not a sequence of independent actions each meant to do something on their own the moment they happen.

Session-state key naming as a real design convention, not an accident

Looking across the whole app, session-state keys fall into two deliberate categories:

  • Fixed, global keys — generating_notes, solving_pyq, selected_doc — used for state that is genuinely singular across the whole app session: there is only ever one "currently selected document," and only one notes-generation call can be in flight at a time (the Generate button is disabled while _BUSY, so a second one can't start anyway).
  • Dynamic, ID-suffixed keys — fixing_weak_{doc_id}, quiz_results_{doc_id}, skip_{doc_id}_{concept_id}, expanding_pyq_{...} — used for state that must be tracked per document, per concept, or per question, because more than one of those can legitimately be mid-flight, mid-review, or storing separate results at the same time. A single shared quiz_results key, for instance, would silently overwrite one document's quiz results the moment a different document's quiz was taken in the same session — the ID suffix is what keeps each document's state genuinely independent inside the one shared session_state dictionary.

This is the direct reason _is_busy() (above) has to prefix-scan session_state instead of checking a short fixed list — the dynamic-key convention that makes per-document state correct is the same convention that makes a busy check unable to just look up one well-known key name.

What this model honestly can't do

Being direct about the real limits of this architecture matters for a professor conversation as much as explaining what it does do. Streamlit's rerun model, as used in this app, has no true background-job system — nothing keeps running independently once a script run ends, and there is no way for a finished background task to reach back in and update a page the student has since navigated away from. There is no websocket-style push mechanism the app's own code uses to notify the browser of anything (Streamlit's underlying transport does use a persistent connection to send rerun output, but the app's Python code never sends an update outside of an active rerun the way a genuine push notification would). And outside of the narrow st.empty() placeholder trick used for the progress checklist, there is no partial-page update — every other state change in this app, no matter how small, requires triggering and waiting through a full top-to-bottom script rerun to become visible. The busy overlay, the flag-then-rerun pattern, and the placeholder-based checklist are not incidental implementation choices — they are the specific, deliberately-built workarounds this app needed because Streamlit's rerun model doesn't give any of that to a developer for free.

12 Known gaps & rough edges

Every section so far has, where it mattered, been honest in the moment about a specific limitation — the Verifier's non-auditability, the remediation cap's honest handoff, the missing enforcement behind the flashcard schedule. This section pulls all of those together in one place, deliberately, rather than leaving them scattered across nine sections a reader would have to remember individually. A professor asking "what doesn't this app do well, and why" deserves this list stated plainly, up front, not discovered piecemeal.

1. The spaced-repetition schedule has no active enforcement

Covered in depth in Section 9 and directly in chat before this section was written: box_level and next_review_at are tracked correctly, and the Flashcards tab now shows a genuine "Due for review" split so the schedule is at least visible. But nothing in the app pushes that information at a student — there's no notification, no reminder email, no in-app badge that appears outside of actively opening that one tab, and no penalty or escalation if a due card is simply never revisited. A card that's been overdue for a month looks identical to one that just became due a minute ago; the app has no concept of "how overdue," only "due or not." This is a genuinely passive implementation of an idea whose whole premise (spaced review) usually depends on the student actually returning on a schedule — the app tracks the schedule faithfully but has no way to make sure anyone follows it.

2. The Verifier's judgment is not auditable, and not fully isolated per item

Restated from Section 6, because it's a standing property of the app, not a one-time caveat: the Verifier check has no formula to fall back on the way the dedup similarity check does. There is no way to independently recompute why Groq marked a specific flashcard invalid beyond the short "reason" string it returns — the judgment either gets trusted or it doesn't, with no way to double-check it by hand. And because every surviving item for one concept is sent to Groq in a single batched request rather than one call per item, a given item's verdict is technically formed in a context that also includes every other item in that batch, even though each verdict is nominally "about" just its own numbered item. Neither of these is a bug exactly — they're the accepted cost of using a second LLM as a check instead of a deterministic rule — but they're real, standing limits on how much confidence the verification step can honestly claim.

3. "Fails open" on Verifier failure is a standing risk, not just a one-off tradeoff

Also from Section 6: if the Groq call itself fails (rate limit, outage, network issue), the app lets that batch's content through unverified rather than blocking it. This was a deliberate, reasoned choice — a temporary third-party outage shouldn't punish a student by discarding an entire concept's already shape-valid content — but it does mean there is a real, currently-unmeasured window where content reaches a student having only passed shape-filtering (Section 5), not the actual truth/relevance check. It has never been logged or surfaced anywhere how often this actually happens in practice; the app has no dashboard or count of "how many items were let through unverified this session."

4. pyq_solutions.matched_concept is a soft link, not a guaranteed one

From Section 9: this field is free text the model produces when asked to name the closest-matching concept, not a real foreign key to an actual concepts row. A PYQ solution's matched-concept label can, in principle, fail to correspond to any real concept in the document (different phrasing, a slightly different name) with nothing in the schema catching that mismatch. Anything that wants to reliably cross-reference a PYQ answer back to its concept has to do its own best-effort text comparison — there's no guaranteed join to lean on.

5. The remediation loop has a real, hard ceiling on how much it can help

Section 8's three-attempt cap is presented there as an honest design choice, and it is one — but restated as a gap: the app has no way to actually diagnose why a student is stuck beyond a single, generic "is there a prerequisite concept" check run once at the cap. A student whose confusion doesn't fit that one diagnostic question (a language/phrasing issue with the notes themselves, a misconception the misconception-notes mechanism doesn't capture cleanly, a gap the notes never covered at all) gets the same generic handoff message as any other stuck student. The app is honest about handing off to a human at that point, but it has no finer-grained way to help before reaching it.

6. Everything assumes one student, one machine, one browser tab

From Sections 9 and 11: SQLite has no real concurrent-write handling built in, and st.session_state is scoped to a single browser session — there is no login system, no user accounts, and no mechanism to separate one student's data from another's beyond "whatever's in this one local studymate.db file." This is a correct, deliberate match for the project's actual use case (a single MBA student running this locally for their own coursework), not an oversight — but it does mean the app would need real, non-trivial rework (a proper database, authentication, per-user data isolation) before it could ever serve more than one person at a time, which is worth stating plainly rather than leaving implicit.

7. The 30-second retry ceiling is a blunt instrument

Every LLM call in this app (Gemini and Groq alike) is wrapped in a retry mechanism that gives up after 30 seconds of total waiting, deliberately lowered from an original 120-second cap. The reasoning is sound and worth stating precisely: Streamlit's native Stop control can interrupt a script that's actively executing Python, but it cannot interrupt a call that's genuinely blocked inside network I/O waiting on a slow or rate-limited API response — so this 30-second cap is the only thing that actually unsticks the app if a call is taking too long, tuned for a bearable worst-case wait rather than maximum retry patience. The real cost of that same choice: a call that would have eventually succeeded on a fourth or fifth retry past 30 seconds — genuinely possible under a rate limit with a longer suggested backoff — gets treated exactly the same as a call that was permanently broken. The app can't currently tell "slow but would have worked" apart from "actually stuck," and errs toward giving up rather than waiting longer, every time.

8. No automated tests anywhere in the project

There is no tests/ directory, no test_*.py or *_test.py file, and no test framework (pytest or otherwise) listed in requirements.txt — confirmed by checking the repository directly, not assumed. Every piece of behavior described across this entire document — the dedup threshold, the marks-to-points table, the remediation cap, the busy-overlay logic — has been verified by hand, through manual use of the running app, not by any test suite that would catch a regression automatically if one of these pieces of logic were changed later. For a coursework project built and iterated on primarily through direct testing and observed behavior (as several sections of this document describe — the PYQ length-control iterations, the prompt-placement discovery), this is a reasonable, honest tradeoff of engineering effort against the project's scope — but it does mean nothing in this codebase is protected against a future change silently breaking something that currently works.

13 Glossary

A quick-reference list of every technical term used across Sections 1-12, in plain language. This section is a lookup aid, not an argument — each entry is short on purpose, and points back to the section where the full explanation lives.

Agent

One of the eight specialized units this app uses to do a specific job: Orchestrator, Summarizer, Flashcard Maker, Quiz Maker, Verifier, PYQ Solver, and Vision Reader each make real AI calls; Style Rules is the eighth, a non-AI shared rulebook every other agent consults. See Section 4.

API / API call

A single request sent to an external AI service — Gemini or Groq — over the internet, asking it to do something (summarize text, judge a flashcard, etc.) and getting a response back.

Box level

Which of the five Leitner spaced-repetition tiers a flashcard currently sits in (1 through 5). A higher box means the card is reviewed less often because the student has been getting it right. See Section 9.

Content-forcing

The PYQ length-control approach that finally worked: instead of asking for a word count or paragraph count (both of which a model can game), the prompt requires specific pieces of content — a definition, a second example, a contrast, a risk — that are much harder to fake without actually engaging with the material. See Section 7.

Dedup / deduplication

The similarity check that catches and discards a flashcard (or glossary term) that's too close to one that already exists, using the SequenceMatcher formula and a 0.75 threshold. See Sections 5 and 6.

Denormalization

Deliberately storing a value in more than one place, or referencing more tables than the strictest relational design would require, for simplicity or query speed — used for quiz_attempts referencing both quiz_questions.id and concepts.id directly. See Section 9.

Fail open / fail closed

Two opposite ways to handle a check that itself can't run. "Fail open" lets the content through unchecked (what this app does when the Verifier's API call fails); "fail closed" would reject everything instead. See Section 6.

Foreign key

A database column that's guaranteed by the schema to point to a real row in another table. Contrasted in this app with a "soft link" — pyq_solutions.matched_concept — which is just plain text with no such guarantee. See Section 9.

Grounding text

The actual source material a piece of generated content is checked against — for this app, the uploaded notes plus a concept's own previously-generated summary, combined. Used both to generate new content and to verify it. See Section 5.

JSON

A structured, machine-readable text format (nested key-value pairs and lists) used both for how AI models return their answers to this app, and for how some database columns (like a quiz question's options) store list/dictionary data inside a single text field.

Leitner system

A specific, well-established spaced-repetition scheme — numbered "boxes," each with a fixed review interval, where a correct review moves a card up a box and a wrong one drops it straight back to box 1. This app's flashcard scheduling implements this exact system. See Section 9.

LLM (large language model)

The general category of AI model this app is built on top of — Gemini and Groq are both LLMs, trained on large amounts of text and able to read, reason about, and generate natural language.

Marks weight

The point value a PYQ question is stated as being worth (e.g. "10 marks"), captured during extraction and used as the primary signal for how developed that question's answer needs to be. See Section 7.

Migration (schema migration)

A change to a database's table structure (adding a column, for instance) applied to a database file that may already exist with data in it, without losing that data. This app handles migrations with a small hand-written additive-column check (_migrate()) rather than a dedicated migrations framework. See Section 9.

Multi-agent system using a sequential pipeline architecture

This app's precise architectural classification: multiple distinct agents (not one), coordinated centrally (not talking to each other directly), by plain deterministic code rather than an LLM-driven orchestrator, running one after another rather than in parallel or adaptively. See Section 4.

Pipeline

The plain, deterministic Python code that calls each agent in order and passes results between them. Explicitly not itself an agent — it makes no AI calls of its own, it just coordinates. See Section 4.

Rerun

Streamlit's core unit of execution: the entire app.py script running again from the very first line, triggered by any user interaction or an explicit st.rerun() call. See Section 11.

Session state (st.session_state)

The one piece of Streamlit state that survives a rerun — a dictionary tied to one browser session, used to remember things like which document is selected or whether a generation call is in progress. See Section 11.

Shape-filtering

The first, non-AI layer of content quality control: checking that a generated flashcard or quiz question is structurally well-formed (real text in the right fields, not a stray JSON blob) before it's even sent to the Verifier. See Section 5.

Similarity threshold (0.75)

The specific cutoff used by this app's dedup check: two pieces of text scoring 0.75 or higher on the SequenceMatcher similarity formula are treated as duplicates. See Section 6.

Thinking budget

An optional Gemini setting that lets the model reason internally before committing to its final answer, instead of writing linearly from the first word. Used only for substantial PYQ answers, never for high-volume calls, because it adds real latency. See Section 7.

Verification / Verifier

The second, real-AI-model layer of content quality control (after shape-filtering): a Groq call that judges whether a flashcard or quiz question is both grounded in the notes and actually on-topic for the concept it's filed under. See Section 6.

B1 Foundation utilities

Files covered: services/json_utils.py, services/logging_setup.py, services/note_parser.py

Why these three files are grouped on one page

None of these three files talks to an AI model, and none of them is one of the 8 named agents. They're all small helper files that other code quietly leans on. Each one does one unrelated job, which is also why they're three separate files instead of one big utils.py: json_utils.py only deals with cleaning up AI output, logging_setup.py only deals with writing logs, note_parser.py only deals with reading uploaded files. Keeping them apart means if you open one of these files, everything inside it is about that one job — nothing mixed in from somewhere else.

File 1: json_utils.py

What this file is for. When the app asks Gemini or Groq for an answer in a specific format (like {"flashcards": [...]}), the model almost always replies in that exact shape — but not always. Sometimes it sends back a plain list instead of the wrapped object, or puts a number where text was expected. If every part of the app read that response directly (like result["flashcards"]), one weird reply from the model would crash the whole thing. This file exists so nothing else in the app has to deal with that risk directly — everything reads the model's response through these functions instead, and a bad reply just quietly turns into "nothing here" instead of an error.

Top of the file. There's a short comment at the top explaining the same thing above. The only import is import json, which is used later by looks_like_json_blob to test whether a piece of text is actually JSON. Nothing else in the file needs anything beyond plain Python.

def safe_get_list(result, key: str) -> list:
    if isinstance(result, list):
        return result
    if isinstance(result, dict):
        value = result.get(key, [])
        return value if isinstance(value, list) else []
    return []

safe_get_list(result, key) pulls a list out of the model's response. Normally result is a dict and the list is stored under key, so it just returns result[key]. But if the model skipped the wrapping and sent back a plain list directly, this function notices that too and just returns it as-is. If neither of those is true — it's not a dict, not a list, or the key doesn't hold a list — it returns an empty list instead of crashing. So whatever calls this function can always safely loop over what comes back, no extra checking needed.

def safe_get(result, key: str, default=""):
    if isinstance(result, dict):
        return result.get(key, default)
    return default

safe_get(result, key, default) is the same idea but for a single value instead of a list — a bit of text, a number, whatever. If result isn't even a dict, it just returns whatever default was passed in instead of crashing.

def safe_get_str(result, key: str, default: str = "") -> str:
    value = safe_get(result, key, default)
    return value.strip() if isinstance(value, str) else default

safe_get_str(result, key, default) calls safe_get above, then adds one more check: is what came back actually text? If the model sent a number or a list where text was expected, calling .strip() on it directly would crash. This function checks first, and only strips (removes extra spaces) if it's really a string — otherwise it falls back to default.

def looks_like_json_blob(text: str) -> bool:
    if not isinstance(text, str):
        return False
    stripped = text.strip()
    if not stripped or stripped[0] not in "{[":
        return False
    try:
        parsed = json.loads(stripped)
    except (json.JSONDecodeError, ValueError):
        return False
    return isinstance(parsed, (dict, list))

looks_like_json_blob(text) catches a specific, strange mistake the model sometimes makes: instead of writing a plain answer, it writes a chunk of raw JSON into a text field — for example, a flashcard's answer coming back as {"explanation": "...", "key_terms": [...]} instead of an actual sentence. Here's what each line does: first, if text isn't even a string, return False right away. Then check the very first character after trimming spaces — if it isn't { or [, it can't be JSON, so return False immediately without doing any real work. Only if it passes that quick check does the function actually try to parse it as JSON with json.loads. If parsing fails, it's not JSON, so return False. If parsing succeeds, the last line checks the parsed result is a dict or list (not just a plain number or string that also happens to parse) — only then does it return True. This connects to Section 5: a flashcard whose answer trips this check gets thrown out before it's even checked for accuracy, because a real JSON object is never a legitimate plain-text answer.

File 2: logging_setup.py

What this file is for. Every part of the app that wants to print a log message (like "5 flashcards survived filtering") calls a function from this file to get its logger, instead of setting one up itself. That way logging always behaves the same way everywhere, and it's set up in exactly one place.

Top of the file. A short comment says this file logs to both the console and a file on disk. Two imports: logging is Python's built-in logging tool that this whole file is built around, and Path (from pathlib) is used to build a file path in a way that works the same on Windows and other operating systems.

LOG_PATH = Path(__file__).resolve().parent.parent / "data" / "studymate.log"
_configured = False

def get_logger(name: str) -> logging.Logger:
    global _configured
    if not _configured:
        LOG_PATH.parent.mkdir(parents=True, exist_ok=True)
        logging.basicConfig(
            level=logging.INFO,
            format="%(asctime)s %(levelname)s %(name)s: %(message)s",
            handlers=[
                logging.FileHandler(LOG_PATH, encoding="utf-8"),
                logging.StreamHandler(),
            ],
        )
        _configured = True
    return logging.getLogger(name)

LOG_PATH is just the file location: data/studymate.log, worked out relative to this file's own location on disk.

_configured starts as False and is used to make sure the setup below only happens once, explained next.

get_logger(name) is the one function in this file, and every other file in the app calls it. The first time it's ever called, _configured is still False, so it runs the setup: makes sure the data folder exists, then calls logging.basicConfig(...) to say "every log message should include the time, the level (like INFO or ERROR), and which part of the app it came from, and should be sent to two places" — a file (FileHandler, writing to LOG_PATH) and the console (StreamHandler). Right after that it sets _configured = True. Every later call to get_logger skips that whole setup block because _configured is now True — it just goes straight to the last line, logging.getLogger(name), which hands back a logger labeled with whatever name was passed in (usually the calling file's own name), so log messages show which part of the app they came from.

Why two log destinations. The console output disappears the moment the terminal is closed or scrolled past. Writing the same messages to a real file on disk means they're still there afterward, if something needs to be checked after a run has already finished.

Why the _configured check matters. Many different files call get_logger. If the setup code (logging.basicConfig) ran every single time instead of just once, log messages could end up getting printed twice, or the setup could behave inconsistently. The flag makes sure the one-time setup really only happens one time, no matter how many files ask for a logger.

File 3: note_parser.py

What this file is for. When a student uploads a notes file, it needs to become plain text before anything else in the app can use it. This file's whole job is: take the raw uploaded file, figure out what kind of file it is, and turn it into plain text. It only handles files that already contain real text (PDF, Word, PowerPoint, plain text) — a scanned photo with no actual text in it is a different case, handled separately by Vision Reader (an AI agent, covered in Phase A) using an AI model to actually read the image.

Top of the file. A short comment says the file turns uploaded notes into plain text. Four imports: io is a standard Python tool used to treat raw bytes like a file, since the three library readers below all expect something file-like rather than raw bytes. PdfReader (from pypdf), Document (from python-docx), and Presentation (from python-pptx) are the three outside libraries that actually know how to read each file format — already named in Phase A's tech-stack section.

def parse_pdf(file_bytes: bytes) -> str:
    reader = PdfReader(io.BytesIO(file_bytes))
    return "\n".join(page.extract_text() or "" for page in reader.pages)

parse_pdf wraps the raw bytes in io.BytesIO so PdfReader can read them like a file, then goes through every page and pulls its text out with page.extract_text(). The or "" part matters: if a page has no readable text at all (common for a scanned image-only page), extract_text() can return None, and trying to join a None value with the other pages' text would crash the whole function. The or "" quietly turns that None into an empty string instead, so the rest of the document still comes through fine.

def parse_docx(file_bytes: bytes) -> str:
    doc = Document(io.BytesIO(file_bytes))
    return "\n".join(p.text for p in doc.paragraphs if p.text.strip())

parse_docx is the simplest one. Document reads the Word file and gives back a list of paragraphs. This line keeps only the paragraphs that actually have text in them (if p.text.strip() skips blank ones — empty lines used just for spacing) and joins the rest with line breaks.

def parse_pptx(file_bytes: bytes) -> str:
    prs = Presentation(io.BytesIO(file_bytes))
    chunks = []
    for slide in prs.slides:
        for shape in slide.shapes:
            if shape.has_text_frame and shape.text_frame.text.strip():
                chunks.append(shape.text_frame.text)
            if shape.has_notes_frame if hasattr(shape, "has_notes_frame") else False:
                chunks.append(shape.notes_frame.text)
        if slide.has_notes_slide and slide.notes_slide.notes_text_frame:
            note_text = slide.notes_slide.notes_text_frame.text
            if note_text.strip():
                chunks.append(note_text)
    return "\n".join(chunks)

parse_pptx is the longest of the four, because a slide's text isn't all in one place. Going through it line by line:

  • chunks = [] — an empty list that collects every bit of text found, added to as the function goes.
  • for slide in prs.slides: — goes through every slide in the file, one at a time.
  • for shape in slide.shapes: — inside each slide, goes through every object on it — a "shape" is PowerPoint's word for anything placed on a slide: a text box, a title, an image, anything.
  • if shape.has_text_frame and shape.text_frame.text.strip(): — checks if this particular shape actually contains text at all (an image wouldn't) and that the text isn't just blank. If both are true, that text gets added to chunks.
  • if shape.has_notes_frame if hasattr(shape, "has_notes_frame") else False: — this line looks confusing, so worth reading slowly: it's checking "does this shape even have a has_notes_frame property at all? If yes, check it. If not, just treat it as false." In practice, individual shapes in this library never actually have that property — speaker notes belong to the whole slide, not to one shape on it — so this check is always false and this line never actually does anything. It's leftover defensive code that doesn't cause harm, it just never runs.
  • if slide.has_notes_slide and slide.notes_slide.notes_text_frame: — this is the line that actually matters for notes: it checks whether this slide has a speaker-notes section at all.
  • The next three lines pull the actual notes text out, check it isn't blank, and add it to chunks too.
  • return "\n".join(chunks) — once every slide has been gone through, all the collected text pieces are joined together with line breaks into one block of text.

Why bother with speaker notes at all: students sometimes write real explanations in the notes section under a slide, not just in the visible bullet points. Skipping that would throw away real content.

def parse_txt(file_bytes: bytes) -> str:
    return file_bytes.decode("utf-8", errors="ignore")

parse_txt is the simplest of all four — a plain text file is just decoded from raw bytes into a readable string. errors="ignore" means if a few bytes in the file don't decode cleanly (a rare encoding mismatch), those bytes are just skipped instead of the whole thing failing.

PARSERS = {
    ".pdf": parse_pdf,
    ".docx": parse_docx,
    ".pptx": parse_pptx,
    ".txt": parse_txt,
}

def parse_uploaded_file(filename: str, file_bytes: bytes) -> str:
    ext = "." + filename.rsplit(".", 1)[-1].lower()
    parser = PARSERS.get(ext)
    if not parser:
        raise ValueError(f"Unsupported file type: {ext}. Supported: {list(PARSERS)}")
    text = parser(file_bytes)
    if not text.strip():
        raise ValueError("No extractable text found in this file.")
    return text

PARSERS is a lookup table matching each file extension to the function that handles it. Instead of writing "if it's a PDF do this, if it's a DOCX do that" as a long chain of if/else, this dictionary just maps the extension straight to the right function.

parse_uploaded_file(filename, file_bytes) is the function everything else in the app actually calls. Line by line: it pulls the file extension off the filename and lowercases it; looks that extension up in PARSERS; if there's no match, it stops and raises an error saying this file type isn't supported. If there is a match, it calls that specific parser function on the file's bytes. Then it checks the result isn't empty once trimmed — if the parser ran but found no real text at all (most commonly a scanned PDF with no text layer, just images of pages), it raises a second, different error saying so. If everything worked, it returns the extracted text.

Why two different errors. "This file type isn't supported" and "this file type is fine but nothing readable was found inside it" are genuinely different problems, and telling them apart in the error message helps the student understand what actually went wrong — the second case is exactly when they'd need to fall back to Vision Reader instead.

Empty. Its only job is to tell Python "the agents folder is a package," so other files can write from agents import orchestrator instead of a messier import path. Contains no functions.

orchestrator.py

What it's for. Two separate jobs that happen before the main generation loop starts: deciding whether an upload is even legitimate study material, and figuring out what distinct concepts/topics the notes actually cover.

  • check_is_study_material(text) — the input-relevance guard we added recently. Sends the extracted text to Gemini and asks whether it's genuinely academic material or something else (a menu, an unrelated document, meaningless text). summarizer.py

What it's for. The Summarizer agent — produces the actual explanation for a concept: what the notes say, what the model adds beyond the notes, an analogy, an exam-answer example, key terms, and "go further" hints. Also handles re-explaining a concept differently for the adaptive loop, and expanding an existing explanation using those hints.

  • summarize_concept(concept, notes, style, depth) — the main function; produces a brand-new explanation for a concept the first time it's generated.

  • reexplain_concept(concept, notes, previous_summary, attempt, style, depth, misconceptions) — used by the adaptive remediation loop (Phase A Section 8) to write a genuinely different explanation when a student is struggling, optionally targeting specific misconceptions from a quiz attempt.
  • _clean_key_term(kt) — internal helper; validates and tidies up one key-term entry from the model's response.
  • _safe_text(result, key) — internal helper; reads a text field out of the model's response safely, rejecting it if it looks like a stray JSON blob instead of real text.
  • _fill_missing_explanation_fields(...) — internal helper; if a required explanation field came back empty or too short, makes one corrective follow-up call to fill in just that field, instead of re-asking for everything.
  • _build_explanation(...) — internal helper; assembles the final explanation text from the separate named fields, calling _fill_missing_explanation_fields if any came back short.
  • ensure_key_terms_count(...) — checks the number of key terms returned against the (style, depth) minimum; if short, makes a follow-up call to extract more terms from the model's own explanation text.
  • _normalize(...) — internal helper; takes the model's raw response and assembles it into the final, consistent summary dict every caller expects.

What it's for. The Flashcard Maker agent — turns a concept's grounding text into a set of front/back flashcards.

  • make_flashcards(concept, notes, n, style, depth) — generates the first-pass set of flashcards for a concept, how many controlled by n (itself driven by Depth).
  • make_drill_flashcards(concept, notes, existing_cards, n, style, depth) — used by the adaptive remediation loop; generates new flashcards for a concept a student is struggling with, given the cards that already exist so it can aim for genuinely new angles instead of near-repeats.

verifier.py

What it's for. The Verifier agent — the real second-AI-model check from Phase A Section 6, judging whether generated flashcards/quiz questions are grounded in the notes and actually on-topic for the concept they're filed under.

  • verify_items(items, notes, concept) — the core function; sends a numbered batch of items to Groq and gets back a verdict (valid or not, plus a reason) for each one.
  • _valid_map(results) — internal helper; turns the raw list of verdicts into a simple lookup so the caller can check "was item 3 valid?" quickly.
  • verify_flashcards(flashcards, notes, concept) — calls verify_items specifically for flashcards (checking their "front" text) and filters the flashcard list down to only the ones that passed.
  • verify_quiz_questions(questions, notes, concept) — same idea, for quiz questions.

quiz_maker.py

What it's for. The Quiz Maker agent — turns a concept's grounding text into multiple-choice quiz questions, each with a correct answer and a reason for why each wrong option is wrong (used to show a misconception note when a student picks it).

  • _is_valid_question(question) — internal helper; checks a single question has the right shape (real question text, a real options list, a valid correct-index) before it's kept.
  • _shuffle_options(question) — internal helper; randomizes the order of a question's options (and updates correct_index to match) so the correct answer isn't always in the same position.
  • make_quiz(concept, notes, n, style, depth) — generates the first-pass quiz for a concept.
  • make_followup_quiz(concept, notes, n, style, depth) — used by the adaptive remediation loop; generates a fresh quiz for a concept after remediation, to check whether the gap actually closed.

pyq_solver.py

What it's for. The PYQ Solver agent — the whole PYQ subsystem from Phase A Section 7. Reads questions off an uploaded question paper, then later writes model answers for them once real concepts exist to match answers against.

  • _parse_questions(raw_items) — internal helper; turns the model's raw extracted-question response into a clean, consistent list of question dicts (text + marks).
  • extract_questions_from_images(images) — reads questions off photographed/scanned question paper pages.
  • extract_questions_from_text(text) — reads questions off a question paper that was already extracted to plain text (PDF/DOCX/PPTX/TXT).
  • _group_into_chunks(questions, depth) — internal helper; splits questions into the solo-vs-batched groups described in Phase A Section 7 — substantial questions solved alone, short ones batched together.
  • solve_questions(questions, concepts, notes, ...) — the main solving function; writes a model answer for every question, matching each one to the closest concept and using the marks-driven content-forcing approach.
  • expand_answer(question, matched_concept, current_answer, hints, notes, style) — the function behind PYQ's own "Expand answer" feature, extending an existing model answer using its current hints.

style_rules.py

What it's for. The shared, non-AI rulebook every other agent in this folder reads from — Phase A Section 3 in full. Not an agent itself (makes no AI calls), but every agent depends on it for consistent style/depth behavior. Holds the raw data (STYLE_RULES, DEPTH_PARAMS, KEY_TERMS_COUNT, FLOW_RULES, and related tables) plus the functions that turn that data into prompt text.

  • _depth_rules_text(style, depth) — internal helper; builds the depth-specific instruction block (exam answer length, key terms count, expand-hints count, comparisons) for a given (style, depth) pair.
  • style_depth_block(style, depth) — the full style + depth instruction block, for the Summarizer only (its schema has depth-specific fields other agents don't).
  • style_only_block(style) — just the vocabulary/tone/flow rules, safe for any agent regardless of its own schema; used by Flashcard Maker, Quiz Maker, and PYQ Solver.
  • concept_granularity_text(depth) — returns the instruction text controlling how many concepts Orchestrator should aim to extract at a given Depth.
  • exam_answer_length(depth) — returns the target length text for a concept's exam-answer example at a given Depth.
  • _high_marks_answer_spec(min_points) — internal helper; builds the "N fully-developed points" instruction text for a substantial PYQ answer, per the marks-to-points table from Phase A Section 7.
  • pyq_answer_length(marks, depth) — decides how long a PYQ answer should be, based on the question's marks weight (falling back to Depth if no marks were captured).
  • pyq_needs_thinking(marks, depth) — decides whether a PYQ answer is substantial enough to turn on Gemini's thinking budget.
  • flashcard_n(depth) / quiz_n(depth) — return how many flashcards/quiz questions to request at a given Depth.
  • explanation_fields(depth) — returns which named explanation fields (core/detail/example) apply at a given Depth.
  • explanation_fields_schema(depth) — returns the JSON schema text for those fields, to embed directly in the Summarizer's prompt.
  • key_terms_min(style, depth) — returns the minimum acceptable key-terms count for a (style, depth) pair.
  • escalated_explanation_fields(depth, attempt) / escalated_explanation_fields_schema(depth, attempt) — like the two functions above, but for the adaptive loop's re-explanation, which escalates to a richer schema on repeated attempts rather than reusing the schema that already failed to get the concept across.
